## 0. How to run this session

This spec has three parts with two hand-offs. **Part 1** is one unattended Opus session that produces
every artefact and proves everything that can be proved without touching the VPS. **Part 2** is Rohan,
following `docs/deploy-runbook.md`, which Part 1 writes. **Part 3** is a short Opus session after Rohan
says "it is live": the browser smoke against the real URL, the cold-load measurement, the baselines,
and the hand-off to a verifier.

Read this whole file, then `CLAUDE.md` (and the session-start protocol it points at), then
`studio/STATE.md`, `studio/features/F-deploy.md`, `docs/hosting.md` (it is wrong in places; §3 says
where), `tools/deploy/nginx-mimas.conf`, `tools/smoke/browser-smoke.mjs`,
`MimasClient/Assets/_Game/Editor/WebBuild.cs`, `server/Mimas.Server/Program.cs`,
`server/Mimas.Server/Mimas.Server.csproj`, `studio/runs/R-2026-09-18-T-0003.md` (the last time the
Web build met a browser), and `docs/networking.md` lines 10–20 (how the client picks its socket URL).

Rules for Part 1:

1. **Autonomous.** No questions. Forks have defaults in §13.
2. **The VPS is not yours to touch.** Part 1 must not run `ssh hostinger` for anything but the two
   read-only checks named in §8 step 1, and must never run `tools/deploy/deploy.sh` without `--dry-run`.
   Rohan runs the deploy. This is his decision (22 Sep 2026), not a limitation to work around. The
   alias exists on this machine precisely so that it *could* be automated later; that "later" is not
   this session.
3. **Commits:** small commits to `main`, `area: what`, in the order of §12. Do not push. Before every
   commit: `dotnet build Mimas.slnx`, `dotnet test shared/Mimas.Core.Tests`,
   `dotnet test server/Mimas.Server.Tests`, all green.
4. **Order of work.** §4 (server), §5 (deploy files), §6 (smoke timing), §7 (runbook), §8 (local
   proof), §9 (docs). Nothing in Part 1 needs the Unity Editor open except the one Web build in §8,
   which runs in batch mode through the script. If `unity status --format json` is not `ready` and the
   batch build cannot open the project, use the existing `Build/Web` from 18 Sep for the local proof
   and say so in the run report; the deploy script is still written to build.
5. **Golden rules** 1, 2, 7, 10 apply. `Build/` is git-ignored and stays so; `Build/Server` lands under
   it. No `.meta`, no `ProjectSettings` edits by hand. `WebBuild.Build` writes
   `ProjectSettings.asset` and `GraphicsSettings.asset` itself; if `git status` shows them modified
   after the build, leave them uncommitted and name them in the run report.
6. **No secrets in the repo.** The VPS is reached only through the ssh alias `hostinger` (in Rohan's
   `~/.ssh/config` on Windows and in WSL). No IP, no user, no key path appears in any committed file
   except the hostname `mimas.laststep.cloud` and the alias name.
7. **Studio protocol.** Task `T-0007` is the running task. Open `studio/runs/R-<date>-T-0007.md` from
   `E:/Studios/Trinetra-Game-Studio/studio/templates/run-report.md` before writing code and append as
   you go. The asset guard has false positives (STATE lists six); restructure a blocked read-only
   command, never rephrase it to slip past, and record it in the run report.
8. **No scope creep.** Out of scope: a custom Web template (STATE: after deploy is green), Docker, a
   CDN, monitoring or alerting, a GitHub Actions pipeline, a `mimas` DNS wildcard, HTTP/3, an origin
   check on the WebSocket handshake (noted in §13 as a follow-up), any change to the game, and
   anything on the VPS that is not Mimas's own nginx file, systemd unit, user and two directories.

## 1. Goal and result

A friend clicks `https://mimas.laststep.cloud`, sees Unity's loading bar, lands in the lobby, and
joins Rohan's room by code or by the invite link. The socket is `wss://mimas.laststep.cloud/ws`,
proxied by nginx to `Mimas.Server` on the loopback interface, run by systemd as a dedicated user.
Deploying again is one command Rohan runs from Git Bash on this PC. Rolling back is one command.
The VPS's other tenants (`laststep.cloud` and its subdomains, sixteen Docker containers, a webhook
service) are untouched.

Concretely, after all three parts:

- `curl -sI https://mimas.laststep.cloud/` is `200`, `text/html`, `Cache-Control: no-cache`.
- The four hashed files under `/Build/` are served with `Content-Encoding: br`, the right inner
  `Content-Type` (`application/wasm` for the wasm), and `Cache-Control: … immutable`.
- `curl -s https://mimas.laststep.cloud/health` returns the server's JSON with `"ok":true`.
- `node tools/smoke/browser-smoke.mjs --url https://mimas.laststep.cloud/ --expect "\[NetClient\] connected"`
  exits 0.
- Two browsers on two networks played a match; the second seat was not Rohan.
- `docs/roadmap.md` baselines has a cold-load number instead of a dash.

## 4. Server change (`server/Mimas.Server`)

One change, `Program.cs` line 17 today:

```csharp
builder.WebHost.ConfigureKestrel(o => o.ListenAnyIP(int.Parse(Environment.GetEnvironmentVariable("MIMAS_PORT") ?? "7777")));
```

becomes: read `MIMAS_BIND` (`any` default, or `loopback`); `loopback` → `o.ListenLocalhost(port)`,
anything else → `o.ListenAnyIP(port)`. Log the bind at startup next to the existing "content loaded"
line: `listening on {Bind}:{Port}`. Dev and tests are unchanged (`any`). The systemd unit sets
`MIMAS_BIND=loopback`. No test is needed for a Kestrel bind, but `dotnet test server/Mimas.Server.Tests`
must stay at 34.

Nothing else in the server changes. `/health` already reports `rooms`, `waitingRooms`, `players`, and
the content hash; the runbook uses `rooms` to tell Rohan whether a deploy would cut a match short.

## 5. `tools/deploy/` — the artefacts

Six files. Every script is `bash`, `set -euo pipefail`, runs under Git Bash on Windows *and* under
Linux, and prints what it is about to do before doing it. Nothing here is interactive.

### 5.1 `nginx-mimas.conf` (rewrite of the existing file; same name)

Keep the structure and every comment that explains a trap (the `add_header` inheritance note, the
`application/wasm` requirement, `gzip off`). Changes:

- `server_name mimas.laststep.cloud;` in both blocks; cert paths
  `/etc/letsencrypt/live/mimas.laststep.cloud/{fullchain,privkey}.pem`.
- Add `include /etc/letsencrypt/options-ssl-nginx.conf;` and
  `ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem;` (both exist on the box, used by the other site).
- Drop the `.gz` locations (this build is Brotli, fallback off; the comment says why they are gone).
- Add `location /TemplateData/ { add_header Cache-Control "public, max-age=3600, no-transform"; }`.
- `location = /health { proxy_pass http://mimas_ws/health; }` (exact match, as today but `=`).
- Add `client_max_body_size 1m;` and `server_tokens off;` in the 443 block.
- Root stays `/var/www/mimas`. `upstream mimas_ws { server 127.0.0.1:7777; keepalive 32; }` stays.
- Header comment: what this file is, that `vps-setup.sh` installs it, that certbot never edits it
  (D8), and that `laststep.cloud`'s file is not ours.

### 5.2 `nginx-mimas-bootstrap.conf` (new)

The port-80-only block that exists just long enough for certbot's nginx authenticator to find a
`server_name mimas.laststep.cloud` and solve the challenge:

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name mimas.laststep.cloud;
    root /var/www/mimas;
    location / { return 404; }
}
```

### 5.3 `mimas-server.service` (new)

```ini
[Unit]
Description=Mimas game server (ASP.NET Core WebSocket rooms)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=mimas
Group=mimas
WorkingDirectory=/opt/mimas/server
ExecStart=/opt/mimas/server/Mimas.Server
Environment=MIMAS_PORT=7777
Environment=MIMAS_BIND=loopback
Environment=ASPNETCORE_ENVIRONMENT=Production
Environment=DOTNET_EnableDiagnostics=0
Restart=always
RestartSec=2
LimitNOFILE=65536
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadOnlyPaths=/opt/mimas/server

[Install]
WantedBy=multi-user.target
```

`ProtectSystem=strict` with a read-only publish folder is correct because the server writes nothing
(no database, no PlayerPrefs on the server, logs go to journald). If Part 3 finds it writing anywhere,
§13 has the fork.

### 5.4 `vps-setup.sh` (new; runs **on the VPS** as root; idempotent)

Installed to `/opt/mimas/deploy/` by `deploy.sh --setup` and run from there. In order:

1. `HOST=mimas.laststep.cloud`. Refuse to run if `hostname -I` does not contain the address
   `getent hosts $HOST` resolves to, with the message "DNS for $HOST does not point here yet; add the
   A record and wait for it" — this is the runbook's step-1 check, enforced.
2. `id mimas` or `useradd --system --home-dir /opt/mimas --shell /usr/sbin/nologin mimas`.
3. `mkdir -p /opt/mimas/server /var/www/mimas`; `chown root:root`, `chmod 755`.
4. If `/etc/letsencrypt/live/$HOST/fullchain.pem` does not exist: install
   `nginx-mimas-bootstrap.conf` to `/etc/nginx/sites-available/$HOST`, symlink into `sites-enabled`,
   `nginx -t`, `systemctl reload nginx`, then
   `certbot certonly --nginx -d $HOST --non-interactive --agree-tos --keep-until-expiring`.
5. Install `nginx-mimas.conf` to `/etc/nginx/sites-available/$HOST` (overwriting the bootstrap),
   `nginx -t`, `systemctl reload nginx`. If `nginx -t` fails, restore the previous file from the
   `.bak` the script took first, reload, and exit 1 — the other site must never stay broken.
6. Install `mimas-server.service` to `/etc/systemd/system/`, `systemctl daemon-reload`,
   `systemctl enable mimas-server`. Do **not** start it: there is no binary until the first release.
7. Print a summary: cert expiry (`certbot certificates --cert-name $HOST`), nginx status, and "next:
   run deploy.sh from your PC".

Every step prints `[setup] …` before it acts and is safe to re-run.

### 5.5 `vps-release.sh` (new; runs **on the VPS** as root)

Called by `deploy.sh` after the upload. Expects `/var/www/mimas.next` and `/opt/mimas/server.next` to
exist. In order:

1. `chmod +x /opt/mimas/server.next/Mimas.Server`; `test -d /opt/mimas/server.next/Data`.
2. Static swap: `rm -rf /var/www/mimas.prev; [ -d /var/www/mimas ] && mv /var/www/mimas /var/www/mimas.prev; mv /var/www/mimas.next /var/www/mimas`.
3. Server swap: `systemctl stop mimas-server` (ignore failure on first release), same three-way move
   under `/opt/mimas/`, `systemctl start mimas-server`.
4. Wait up to 15 s for `curl -fsS http://127.0.0.1:7777/health` to answer; print it. If it never
   answers: `journalctl -u mimas-server -n 40 --no-pager`, then exit 1 (the static files are already
   swapped; `deploy.sh --rollback` undoes both).
5. `--rollback` mode: swap `.prev` back for both, restart, health check.

### 5.6 `deploy.sh` (new; runs **on this PC**, Git Bash or WSL; also fine on Linux)

Usage line, printed on `--help` and at the top of the file:

```
bash tools/deploy/deploy.sh                 build, publish, upload, release, health check
bash tools/deploy/deploy.sh --skip-build    reuse Build/Web (the last Web build)
bash tools/deploy/deploy.sh --dry-run       print every command, run none of the remote ones
bash tools/deploy/deploy.sh --setup         one-time: upload tools/deploy to the VPS and run vps-setup.sh
bash tools/deploy/deploy.sh --rollback      put the previous build and server back
bash tools/deploy/deploy.sh --smoke         after release, run the browser smoke against the live URL
```

Variables at the top, overridable from the environment: `MIMAS_SSH=hostinger`,
`MIMAS_HOST=mimas.laststep.cloud`, `MIMAS_SIZE_LIMIT_MB=25`. Steps for a plain run:

1. Must be run from the repo root (`test -f Mimas.slnx`). `git status --porcelain` non-empty → print
   a warning (the build's provenance file records `dirty: true`), continue.
2. `ssh -o BatchMode=yes "$MIMAS_SSH" true` — fail early with "the ssh alias $MIMAS_SSH does not
   work; see docs/deploy-runbook.md §0".
3. Build (unless `--skip-build`): `export MSYS_NO_PATHCONV=1`, then
   `unity build MimasClient --target WebGL --execute-method Mimas.Client.Editor.WebBuild.Build --output-path Build/Web`
   exactly as `R-2026-09-18-T-0003.md` line 302 ran it. Then require `Build/Web/index.html` and
   exactly one `*.wasm.br` under `Build/Web/Build/` (`WebBuild.Build` cleans stale hashes; if there
   are two, something is wrong — stop).
4. Size gate: sum the bytes of `Build/Web/Build/*`; print `MB`; exit 1 above `MIMAS_SIZE_LIMIT_MB`
   with the message from `F-deploy` ("rung 9 gate: build is X MB, limit 25 MB").
5. `dotnet publish server/Mimas.Server -c Release -r linux-x64 --self-contained true -o Build/Server`
   then require `Build/Server/Mimas.Server` and `Build/Server/Data/rules.json`.
6. Upload, both through one ssh each:
   `tar -C Build/Web -czf - . | ssh "$MIMAS_SSH" 'rm -rf /var/www/mimas.next && mkdir -p /var/www/mimas.next && tar -C /var/www/mimas.next -xzf -'`
   and the same for `Build/Server` → `/opt/mimas/server.next`. Print sizes and elapsed seconds.
7. `ssh "$MIMAS_SSH" 'bash -s' < tools/deploy/vps-release.sh`.
8. `curl -fsS "https://$MIMAS_HOST/health"` from this PC, print it; then
   `curl -sI "https://$MIMAS_HOST/"` and assert `200` and `no-cache`; then one hashed `.wasm.br` URL
   read out of `Build/Web/index.html` (the loader config lists it) and assert `content-encoding: br`
   and `content-type: application/wasm`. These three curls are the deploy's own verdict.
9. `--smoke`: `node tools/smoke/browser-smoke.mjs --url "https://$MIMAS_HOST/" --expect "\[NetClient\] connected" --timing --shot artifacts/smoke-live`.

`--setup` uploads `tools/deploy/*.conf`, `*.service`, `vps-setup.sh` to `/opt/mimas/deploy/` (creating
it) and runs `bash /opt/mimas/deploy/vps-setup.sh`, streaming its output. `--dry-run` prints steps 3–9
as commands prefixed `[dry-run]` and executes only steps 1, 2 and the local build/publish/gate if
asked. `--rollback` runs step 2 then `vps-release.sh --rollback` then step 8.

## 6. `tools/smoke/browser-smoke.mjs` — one addition

`--timing`: record `performance.now()`-equivalent wall-clock at `page.goto`, at "booted"
(`createUnityInstance` resolved, the script's existing check), and at the moment `--expect` matches.
Print one line at the end:

```
[timing] boot 4213 ms, expect 6870 ms, transferred 12.4 MB
```

where `transferred` sums `response.headers()['content-length']` (or the body size when absent) over
every response on the page, which is what "cold load" costs the friend. The browser context is already
fresh per run, so there is no cache to disable. No other behaviour changes; the header comment gains a
line for the flag. Verify locally in §8.
