How to use this document

This page is the single source of truth for what Mimas is. Nothing gets built that is not written here first. Code that disagrees with this page is a bug in the code or a missing decision here, never a silent new rule.

The contract

  1. Design first. Before any Core, Server or Client work, the concept it touches must exist here with status decided or proposed. If it does not, add it (as proposed) and get it confirmed, or log a question in the section's Open questions block.
  2. Every concept has two statuses. Design: decided (Rohan confirmed), proposed (a default written by Claude, not yet confirmed), open (no default is safe), superseded (replaced; kept for history). Code: in code, partial, not started, drift (the code implements something different from this page).
  3. Drift is loud. When a section carries drift, the section says exactly what the code does instead and which change is planned. The drift register is generated from these flags.
  4. Link, do not repeat. A rule lives in one section. Other sections link to it with #anchor. Backlinks ("Referenced by") are computed when the page loads, so cross references never go stale.
  5. Numbers are data. Balance values quoted here are the current JSON values and may change without a design decision. Formulas, slots, visibility rules and vocabulary may not.
  6. Architecture goes to the ADR log. Design decisions are recorded here in the decision log; architectural ones also get an ADR in docs/decisions.md. Data schemas are detailed in docs/data.md; this page only sketches them.
  7. Anchors are stable. Commit messages, ADRs and CLAUDE.md cite sections as design/index.html#equipment. Never rename an anchor; add a new section and mark the old one superseded.

Editing checklist (for Claude Code and Rohan)

  • New concept: copy any <section class="concept">, give it a unique id, data-design, data-impl, data-title, place it under the right group.
  • Changed rule: edit the rule, add a line to the changelog, update the statuses. If code now disagrees, set data-impl="drift" and add a .drift-note.
  • Answered question: delete the <li> from the section's open questions, write the answer into the rules, log it in the decision log.
  • Status vocabulary is closed. Do not invent a fifth design status.

Vision and pillars

A browser-based 1v1 turn-based tactics duel on hex maps. A Baldur's Gate 3 fight distilled into a competitive, chess-like ladder game with hidden information and TFT-style power drafting. No story, pure play.

Baldur's Gate 3 (tactical feel, camera), chess (time controls, ladder, clean information model), Teamfight Tactics (augment drafting), Hades (god-granted boon pools), Into the Breach (deterministic, readable combat).

Non-goals

  • No random damage. See Damage.
  • No more than one hero per player at launch. The model is multi-unit ready but summons are a later boon idea.

Loop

Session

A session is one matchmade encounter between two players. It is a best-of-X series of rounds, each on the next map of the ladder, with a draft between rounds. The build (gear, lineage, boons) carries forward for the whole session.

Rules

  1. A session starts after matchmaking pairs two players on the same time control.
  2. Both players go through character select before round 1. Selection is simultaneous and private.
  3. Rounds are played on ladder maps in strict order (decided 21 Sep 2026): round n plays ladder position ((n − 1) mod length) + 1, so with two maps round 3 is back on position 1. The ladder wraps; a third map is a later session, not a rule.
  4. The session ends when one player has won the majority of rounds: best of 3, in data as rules.series.bestOf (odd), so first to bestOf / 2 + 1 (decided 21 Sep 2026; the count does not depend on the time control). See Win conditions.
  5. After every round except the last, both players draft one boon.
  6. Everything learned through reveals stays revealed for the rest of the session.
  7. A player who resigns, or who leaves and does not reconnect within the grace period, forfeits the session (decided 22 Sep 2026, P8) — not the round. A resign inside a round scores that round first and then ends the series; a resign between rounds scores nothing. See Online.
Implemented. Mimas.Core.Session.Session since 22 Sep 2026 (T-0009, ADR-035): a pure state machine that owns the builds, the score, the ladder, the session-long revealed sets and the draft, constructs one MatchState per round from its own seeded RNG, and replays from one seed. The server has hosted it since part 2 (T-0010, ADR-036): one session per Playing room, one whole best-of-3 per Ready; resign and forfeit end it with a reason.

Round

One map, played in alternating turns until one hero dies. The round winner takes a series point.

Rules

  1. Each player has exactly one hero, spawned on their map spawn (p1 / p2) at full health.
  2. Who moves first: round 1 by a seeded coin flip; then the loser of the previous round moves first (decided 21 Sep 2026, D13; Session does exactly this).
  3. The round ends the moment a hero reaches 0 health (by damage or environment).
  4. Between rounds, health, AP and one-round states reset; gear, lineage, boons and revealed knowledge persist.
  5. The round clock (see time controls) restarts per round. A flag fall loses the round, not the session (proposed).

Open questions

  • Does the chess clock reset per round, or is one clock shared across the whole session?
  • Flag fall = lose round or lose session?

Character select

Before round 1, each player builds their hero in two steps, in this order: 1. pick gear (one item for each of weapon, armour, crown, boots), 2. pick a divine lineage to pray to. Simultaneous, private, on a timer.

Rules

  1. Step 1, gear: one item per slot from the full item catalogue. All four slots are mandatory. There are no classes; "warrior" and "mage" survive only as suggested presets in the UI.
  2. Step 2, lineage: one of Greek, Norse, Hindu (Lineage). Shown after gear so the player can pick a god that suits the kit (the lineage's boon pool is filtered by owned gear).
  3. The choice is locked for the session. Gear only changes through Enchants and Sigils.
  4. Selection timer: 60 s (proposed). Timing out picks the last preset the player used, or the default preset.
  5. The opponent sees your gear at round start (public) but never your lineage or starting Blessing until revealed.

Draft (between rounds)

After every round except the last, each player is offered three boons from their lineage's pool and keeps one. The pick is private and simultaneous.

Rules

  1. Offers are drawn with the session seeded RNG, so a replay reproduces them. Player 0's offer is drawn first, then player 1's.
  2. Only boons the player can use are offered: an Enchant or Sigil whose requires does not match the player's gear is excluded, as is one whose ability target the player does not have or whose granted ability they already have; a boon already owned is excluded unless it declares stackable; a boon sharing an exclusive group with an owned one is excluded. The starting Blessing counts as owned.
  3. Offers are one of each kind when possible (one Blessing, one Enchant, one Sigil, in that order); otherwise filled from what remains. Fewer eligible boons than offers means fewer offers, possibly none.
  4. The draft is symmetric (decided 21 Sep 2026, D10): the counts live in data as rules.draft.offers.winner and .loser, both 3 at launch, so a comeback draft is a number change, not a rule change.
  5. Draft timer: rules.draft.timeoutMs, 20 s at launch. Timeout picks the first offer, as a command the host submits (Core never reads a clock).
  6. The pick is hidden. The opponent sees only that a pick was made.
  7. Picks apply immediately and last for the session. No tiers, no rarity, no reroll, no cap at best of 3 (decided 21 Sep 2026, D18): later, not at launch.
  8. Where it happens (decided 22 Sep 2026, P1): over the dimmed board, in the Arena. The round's result shrinks to a headline, the board goes dark behind a scrim, and three cards drop in with kind, name, god, what the boon does and the item of yours it lands on. A click selects, Confirm keeps it, or the timer keeps the first. proposed Their end of the turn track says HAS CHOSEN once the opponent has picked (23 Sep 2026; it was a green dot, and green means "above base" in the UI language). The cards are designed in docs/ui/between-rounds.md. The next round reloads the board for its own map; a reload mid-draft comes back into the draft with the seconds that are left.
Implemented in part 2 (T-0010, ADR-036): the overlay with its three cards and its timer, the server's timeout pick, the bot's pick, and the pick as a draftPick command on the existing wire. Mimas.Core.Session.Draft (22 Sep 2026) is the rules above, pure and seeded.

Open questions

  • Tiers / rarity (TFT silver/gold/prismatic), and whether the tier depends on the round number. Later, not at launch (21 Sep 2026); the data has no tier field yet.
  • A reroll. Later, not at launch (21 Sep 2026).

Turns and action points

Players alternate. On your turn your hero has 3 AP; every ability has a flat AP cost and can be used as often as AP allows. Unspent AP is lost. End Turn passes early; the clock cap passes for you.

Rules

  1. Alternating turns, one actor at a time (ADR-015). No simultaneous planning, no initiative stat.
  2. AP refreshes to the unit's ap stat at the start of its owner's turn (ADR-016). AP lives on the unit, not the player, so summons can arrive later.
  3. An ability costs its cost (default 1, may be 0). No per-turn use limits other than AP; cheap repeatable attacks are a data balance lever.
  4. Legal actions are enumerated by one function (EnumerateLegal) that the HUD, the server and bots all use, so they cannot disagree (ADR-018).
  5. Reaching the per-turn clock cap with no action = skip. The server submits EndTurnCommand(Timeout) so replays need no clock.
  6. An idle skip gives the next turn a short fuse (idle penalty) that resets the moment the player acts. Deferred 17 Sep 2026: not enforced online in M2 (every turn is the full 30 s); the local practice clock keeps it. Revisit with time controls.
  7. Boons may change ap or an ability's cost (e.g. a Blessing "+1 AP", an Enchant "Shot costs 1"). See Stats.

Every turn is 30 s (rules.clock.turnMs), a round ends when a hero dies, and there is no bank, no increment and no time-control choice. Rules

  1. The server is the timekeeper; the client predicts and displays. Every server message carries the turn's remaining time; the client counts down from receipt and re-anchors on each message, so no clock synchronisation is needed.
  2. The server ends a turn at the deadline plus a lag grace of the measured round trip, capped at 1 s (rules.clock.lagGraceMs), so a command that left the client in time is never refused (Lichess compensates lag the same way).

  4. The idle penalty (Turns) is not enforced online in M2.
  5. Draft and character select timers are separate from the game clock.

Win conditions

  1. Round: the opponent's hero reaches 0 health, by damage or by the environment (tile effects, later).
  2. Session: majority of rounds (best of X, see Session).
  3. Resign concedes the session (in M2 a session is one round). Forfeit: a player who does not reconnect within the grace (Online) loses the session. Flag fall: see open question (no bank in M2, so none yet).
  4. Simultaneous death (both heroes at 0 in the same resolution, possible once environment damage exists): the active player loses (proposed, punishes the reckless actor).
Partial. Elimination, resign and forfeit all exist (ResignCommand with reason Player or Disconnect; MatchEndReason.Elimination / Resign / Forfeit), and a resign is legal off turn. Series score and simultaneous death are not in code.

Board

Board: hex tiles, terrain, height

The board is any set of hex tiles (axial coordinates, cube math). Each tile has a terrain, an integer height and optionally a modifier. Shape is data: rings, boards, arenas are all just hex lists.

Rules

  1. Terrain (terrains.json): walkable, moveCost, optional modifiers[] granted to whoever stands on it. Current: grass (walkable, 1), stone (blocking).
  2. Height is a rules value, and it is an integer level. Movement reads levels directly: walking may rise at most maxClimb per step; a jump is blocked by anything more than jumpHeight above the origin. Descending is never limited.
  3. Body units. Sight and trajectories are measured in finer body units, and rules.heights is the conversion: one level is unitsPerLevel units (3), a hero's body is body units above the tile top (6), and every attack leaves from and lands at aim (4). So a level-1 step (top 3) does not block a flat shot between two heroes on the ground, a level-2 plateau (top 6) does, and so does any body standing in the way.
  4. High ground: attacking from a higher tile adds a public flat bonus (global modifier high-ground, currently +2). See Modifiers.
  5. Occupancy: one living unit per tile; dead units occupy nothing.
  6. All geometry is integer-exact (HexLine, ADR-013) so server and client agree bit for bit.

Line of sight

Sight is a straight ray from the attacker's aim point to the target's aim point, over heights in body units. Whether an attack needs it is a per-attack field; how the attack travels is a separate one (Trajectories). Both must pass.

Rules

  1. Aim point = muzzle. The ray runs from tileTop(attacker) + aim to tileTop(target) + aim. Two heroes therefore see each other symmetrically: if I can see you, you can see me.
  2. A column blocks when its top reaches the ray. For a sample at parameter a/b the test is the cross-multiplied integer top·b ≥ h0·(b−a) + h1·a. A graze (equality) blocks. No division, no float, same answer on server and client.
  3. Bodies block. A column's top is the tile top plus the body of any living thing standing there — a hero, a wall, a pillar. The attacker and the target never block themselves.
  4. Endpoints never block, holes in the map never block, and unwalkable terrain is solid: it stops everything except sky, whatever its height.
  5. A grazing line (through a hex edge or corner) is blocked if either flanking hex blocks (supercover), so a shot is never legal in one direction and illegal in the other. Each tile is tested at both of its ends, because a tile is a prism and a flight is lowest at an edge.
  6. Movement's requiresLineOfSight (the teleport) uses this same ray, ignoring the mover's own body.

Props: walls and pillars

A prop is a body that is not a hero: a pillar, a wall. It stands on a hex, occupies it, and blocks movement, sight and trajectories with its height, exactly as a hero does. Cover is a thing on the board, not a kind of terrain.

Rules

  1. Anything with health can be hit; nothing else. A prop with hit points is a legal target with its own aim point; a prop without them is a permanent wall that blocks shots and can never be hit.
  2. Props are neutral (no owner) and entirely public: both players see every prop, its position and its health. Nothing about a prop is hidden.
  3. A destroyed prop is removed: its tile is enterable again and nothing on the board reports it. Killing a prop never ends the round.
  4. Data (props/*.json): bodyHeight (what it blocks with), aimHeight (where shots land, required even for a wall so a client can place a marker), optional stats with hp and per-lane defence. Shipped: pillar (body 6, 10 hp, no armour — about one full turn of damage) and wall (body 6, indestructible).
  5. Placement is a map field: a hex may carry "prop": "<id>". The terrain must be walkable, the hex's 180° twin must carry the same prop, and a spawn may carry none.

Open questions

  • Owned props: shield generators, traps, summons a player places. Needs an owner, a spawn action and a reveal rule. Not at launch.
  • Does a destroyed pillar leave rubble (a low tile, a cost, a half-cover body), or simply vanish? Proposed: it vanishes.

Maps and the ladder

Maps are JSON hex lists with a declared symmetry, two spawns and a ladder position. Every shipped map is validated at boot: symmetric with matching terrain, spawns walkable and at maximal distance, all walkable tiles connected.

  1. Symmetry: rotational-180 implemented; mirror-q reserved.
  2. Spawns are opposite each other at maximum walkable distance (pillar 14).
  3. Ladder: ladderPosition orders maps; lower positions are smaller and simpler, higher ones add height, props and (later) tile effects. Current: board-3 (position 1), arena-4 (position 3).
  4. Heights must be symmetric too (enforced by test only; loader check pending). Props must be symmetric, must sit on walkable terrain, and may not sit on a spawn — all three enforced by the loader.

board-3: a flat radius-3 field, 37 tiles, one stone hex at the centre. Stone is unwalkable and therefore solid: it blocks sight. Unchanged.

Tile effects and pickups

Pillar 4 promises tile effects: bonus pickups, hazards, terrain modifiers. Terrain modifiers exist (a terrain or a hex can grant a modifier to whoever stands on it). Pickups and hazards are not designed.

The movement model already separates Path (what to animate) from EnteredTiles (what tile effects fire for: every tile of a walk, only the destination of a jump or blink), so an OnEnter hook can be added without touching resolvers (ADR-012).

Open questions

  • What can a pickup be: AP, health, a one-round boon, a charge? Does it respawn?
  • Hazards: damage on enter, damage per turn standing, knockback into holes (environment kills)?
  • Are tile effects always public? (Proposed: yes; hidden information lives on characters, not on the board.)
Character

Character

A player's hero is defined by three things and nothing else: gear (four items), a divine lineage, and the boons drafted during the session. There are no classes.

Rules

  1. Derived stats = base values (rules.json) + sum of item stats + Blessing and Enchant stat effects.
  2. Derived ability list = innate movement (walk) + abilities of each equipped item + abilities added by Sigils. Order in the HUD: movement, weapon, spell.
  3. Derived modifier list = Blessings' modifiers + Enchants' modifiers + whatever the tile grants + global rules.
  4. One hero per player. The unit model stays multi-unit ready (per-unit ids and AP).
  5. Nothing about the character is random. Same picks = same character.

Equipment (gear)

Four slots, one item each, all mandatory, locked for the session: Weapon, Crown, Boots, Armour. Items are the only source of stats and abilities besides the lineage.

Rules

  1. An item has: id, slot, kind (bow, gun, blade, … used by boons' requires), stats (any stat keys), abilities[] (ability ids it grants), tags[] (matched by modifiers), one-line description, presentation keys (model, icon).
  2. Item identity is public: the opponent sees the item name and its innate stats. Its ability list is not shown until each ability is used.
  3. Items never change identity during a session. Enchants attach to an item and alter its numbers or add tags; Sigils add abilities to it.
  4. Slots are fixed at four. New item kinds are data; new slots are a design decision.
  5. Items are pure additions: no negative stats, no set bonuses, no anti-synergies. Synergy comes from boons.
  6. Every base weapon and every base crown carries exactly two abilities. Boots carry one movement mode. Armour carries none. (Authoring convention on shipped content, enforced by a repo-data test; the loader itself only requires a weapon to have an attack.)
  7. Launch catalogue (16 Sep 2026): weapons bow and gun; one crown; boots jump and teleport; one armour. Blade (melee) is deferred, not rejected.

Weapon slot

The weapon grants the hero's two weapon-lane attacks and some Strength. Every weapon has a minimum and a maximum range. Kinds at launch: bow and gun. Both hit adjacent enemies; the gun reaches further, the bow hits slightly harder.

Crown slot

"This is where spells come from and are used." The crown grants the hero's spell-lane attacks and Magic. A crown may also carry an innate element.

  1. Every base crown lists exactly two spells. More spells arrive through Sigils.
  2. An Enchant on the crown can add an element to every spell it grants ("fire on crown" = all crown spells are tagged fire and gain a fire rider).
  3. Spells are attacks in the spell lane; they may ignore some targeting rules by data (e.g. minRange). Both shipped spells are direct and need line of sight, but that is data, not a law of crowns.

Open questions

  • Can crowns grant non-damage spells (heal, shield, slow)? Needs an effect vocabulary beyond damage. Proposed: not at launch.

Source: notebook page 1 (Crown).

Boots slot

"Gives different kinds of movement." Every hero can walk innately (1 hex per AP, climb 1); boots grant one extra movement mode (jump, teleport, later fly or dash) and may alter walk parameters.

  1. Walk is innate and never removed; it is listed in rules.innateAbilities rather than on any item.
  2. Boots grant abilities[] (movement kind) and may set walkRange / maxClimb overrides via stats (proposed keys walk.range, walk.climb).
  3. Sigils can add a second movement mode to boots ("teleport on boots").

Source: notebook page 1 (Boots).

Armour slot

Armour negates damage with two separate numbers: defense.weapon and defense.spell. It is also the main source of Health. Plate can be great against weapons and weak against spells; robes the reverse.

  1. Defence is flat and subtractive per hit (see Damage). It never reduces a hit below 0.
  2. Elemental resistances and immunities are not armour numbers; they are modifiers from Blessings or Enchants on the armour.
  3. Armour has no HP pool of its own (ablative armour rejected).

Source: notebook page 1 (Armour negates damage); round-2 answer "separate weapon and spell reduction".

Combat

Abilities

An ability is anything a unit spends AP on. Two types exist: movement and attack. Every ability is data (abilities/*.json) with a flat AP cost, a HUD category (movement, weapon, spell) and an icon. Abilities come from gear and sigils, never from the character directly.

  1. Fields shared by all: id, type, name, description, icon, category, cost (default 1).
  2. An ability's owner is the item that grants it (or the innate list). The HUD groups by category; the examine panel groups by item.
  3. Abilities are hidden from the opponent until first used, even when the granting item is public.
  4. Enchants may alter an ability's numbers (range, damage, cost) through the item they attach to; the ability definition itself is immutable.
Partial. Abilities load and resolve and know their source item; enchant overrides do not exist.

Movement

Movement kinds differ in geometry; everything else is a data table. Modes: walk (path search, terrain cost, climb limit, cannot cross units), jump (straight line, arc clearance by height), teleport (point pick, optionally needs sight). Fly is a walk whose cost table says everything costs 1 plus ignoreHeight.

  1. Destination must exist, be enterable and unoccupied. Origin is never a destination.
  2. Walk refuses to cross occupied tiles; jump and teleport cross anything, including holes, and enter only their destination.
  3. terrainCosts per ability overrides the terrain catalogue (an integer makes even stone enterable; null makes even grass impassable).
  4. A move produces a MovePlan: Path to animate and EnteredTiles for tile effects.
  5. New modes are one resolver class plus one JSON; unknown modes fail closed.
  6. requiresLineOfSight (the teleport) uses the attack ray: from the mover's aim point to the aim height of the destination, ignoring the mover's own body. One sight rule for the whole game.

Source: pillar 12; ADR-012; docs/data.md "Movement abilities".

Attacks

An attack targets one damageable body — an enemy hero or a destructible prop — inside a circular minRange..range band, subject to its own sight requirement and its trajectory. It declares its lane (weapon or spell), a flat base damage, optional element and tags.

{ "version": 1, "id": "fire-bolt", "name": "Fire Bolt", "type": "attack", "category": "spell", "cost": 2,
  "attack": { "damage": 6, "damageType": "spell", "range": 3, "minRange": 1,
              "trajectory": "direct", "lineOfSight": true, "element": "fire" },
  "tags": ["bolt"] }
  1. category is weapon or spell and must match the lane (an attack granted by a crown is a spell; by a weapon, a weapon). HUD only reads category; rules read the lane.
  2. The range band is a circle. In range iff minRange² ≤ q² + qr + r² ≤ range² for the offset target − attacker: the exact squared distance between the two hex centres, in integers, so the client can draw a true circle and be right. Up to 6 it equals hex distance; from 7 up the diagonals reach further. Movement still counts hexes.
  3. Two required fields, lineOfSight and trajectory (plus apex for an arc), and both must pass. There is no default: an attack that declares neither is a content error.
  4. Targets. Anything with health can be hit and nothing else: an enemy hero, a destructible prop. A wall blocks shots but is never a target, and targeting the ground is not legal (the client may preview a landing spot; the rules refuse it).
  5. Targeting and legality come from one function used by HUD, server and bots. A refusal names its reason and, for a blocked shot, the hex that stopped it.
  6. Multi-target shapes (cone, line, area) are not designed; Sigils like Triple Shot will need a shape or a multi-hit count. See open question.
Partial. Lanes are weapon / spell; element exists (22 Sep 2026: Fire Bolt is fire, and an Enchant can add one). attack.hits is a skeleton: it parses and is stored, and a unit whose attack has more than one hit fails closed with a message naming the spec (part 1 §6.7), because the rule is still the open question below. Everything else in this section is in code.

Open questions

  • Multi-hit and area attacks (Triple Shot, Cleave): repeated single resolution vs a shape. Proposed: hits: 3 repeats the single-target resolution; shapes later. The hits field exists as a skeleton; the resolution rule does not.

Trajectories

Two independent fields decide whether an attack is legal. lineOfSight asks whether the attacker must see the target (the ray). trajectory says how the attack travels, and each mode has its own blocking rule. An attack is legal only if both pass.

The three modes

ModeBlocked byShipped by
directThe same ray as sight, by construction.Gun (Quick Shot, Heavy Shot), crown spells (Fire Bolt, Arcane Spark) — all with lineOfSight true.
arcAn integer parabola through the same endpoints, peaking max(h0,h1) + apex at mid-flight.Bow (Arrow Shot, apex 3; Aimed Shot, apex 4) — with lineOfSight false: an arrow may drop behind cover you cannot see past.
skyNothing. Whatever lies between is irrelevant.Nothing yet: it exists in code and test fixtures, waiting for a mortar or a meteor.

Rules

  1. apex (an integer, 0 or more) is required for arc and forbidden for everything else. It is measured above the higher of the two aim points, so the same bow clears the same wall differently depending on where it stands.
  2. The arc is sampled per intervening tile at both of the tile's ends, in integers scaled by b². No float ever touches it.
  3. A bow arrow with apex 3 clears a 6-unit wall two tiles away but not the wall right next to it. That distance-sensitivity is the point: cover should depend on where you stand, not only on what is there.
  4. Unknown modes fail closed and throw. A new mode is one resolver class plus one line in the registry, exactly like movement.
  5. The override seam. Resolution reads trajectory, apex, sight and the range band from the attack definition through one place, so an Enchant can hand it a modified copy without touching the resolvers. No enchant does this yet.

Open questions

A skeleton exists (22 Sep 2026): an abilityOverride on trajectory or lineOfSight parses and links, and a unit built with one fails closed naming the spec. The rule is still open.

Damage

Deterministic. No dice, no hit chance. Two lanes, weapon and spell; each lane has a power stat (Strength or Magic) and an armour defence. Elements and everything else are flat modifiers on top.

damage = max(0,  base
               + power.<lane>            (attacker: Strength or Magic)
               - defense.<lane>          (target's armour, weapon or spell)
               + Σ flat modifiers )      (elements, high ground, blessings, enchants, terrain)
  1. The result is a fixed-order list of signed lines (base, power, defence, then modifiers grouped attacker unit / attacker tile / globals, target unit / target tile / globals, sorted by id) plus the total. This is what the tooltip shows.
  2. Preview and actual are the same function. The preview uses the attacker's knowledge (hidden enemy modifiers dropped and counted as "?"); the server resolves with full knowledge. When they differ, the modifier that caused it is revealed.
  3. Immunity (from a Blessing) is a modifier whose effect nullify sets the total to 0 after everything else. Shown as one line "Immune (fire)".
  4. Percentages are not allowed. If ever needed they are computed in integer basis points, never floats.
  5. High ground applies to every trajectory: the condition is the attacker's tile being higher than the target's, whatever the shot did on the way.
  6. Enemy health is fully visible (pillar 8 surprise lives in abilities and modifiers, not in the health bar).
Partial. Two lanes, nullify (one Nullify line, total 0 after every flat line and the floor), boon stat lines and element riders are in code (22 Sep 2026). The tooltip's "Immune (fire)" wording is presentation, part 2.

Elements and modifier classes

An element (fire, frost, lightning) is a modifier class: a tag an attack carries that resistances, immunities and riders match on. It is not a third damage lane. Other modifier classes (e.g. bleed, holy) can be added the same way later.

  1. rules.json declares elements[]: fire, frost, lightning at launch (decided 21 Sep 2026, D14; lineages share them). An attack may carry at most one innate element; an Enchant can add one to every attack of an item. The elements on an attack are a set (D9): innate plus added, and a rider, resistance or immunity matches on any of them. Element Enchants on one slot share an exclusive group, so the draft never offers two for one item.
  2. A rider is a dealDamage modifier with when.elements and a positive effect.damage ("+2 fire").
  3. A resistance is a takeDamage modifier with when.elements and a negative effect.damage; an immunity uses effect.nullify.
  4. Elements have no rock-paper-scissors table at launch (fire beats frost etc.). Any such interaction is a modifier in data.
  5. Elements are shown as an icon on the ability button and as a line in the damage tooltip.
Partial. rules.elements, attack.element, the element set on a resolved attack, when.elements riders and resistances and nullify immunities are in code (22 Sep 2026). The icon on the button and the tooltip line are presentation, part 2.

Open questions

  • Do elements ever apply a status (burn per turn, frost slows)? Needs a status system; not at launch.

Source: notebook page 2 (Damage types: weapon, spell, elemental); round-1 answer "elemental has its own class (fire, frost, etc), other kinds of damage modifiers later"; 21 Sep 2026 question rounds (D9, D14).

Modifiers

A modifier is one trigger, a conjunction of conditions, and one flat effect. Who owns it is the attachment, never the file: a unit (via Blessing or Enchant), a terrain, a map hex, or the global rules.

Divine

Divine lineage

At character select, after picking gear, the player chooses the divine lineage they pray to. Launch lineages: Greek, Norse, Hindu. A lineage grants one fixed starting Blessing immediately and defines the pool of boons offered in every draft. Lineages shape a build; they do not lock a playstyle.

  1. Each lineage has: id, name, startingBlessing (a Blessing id), pool[] (boon ids), one-line flavour, presentation keys.
  2. The pool must contain all three boon kinds and, for every item in the catalogue, hold at least one Enchant or Sigil applicable to it (its slot and kind match, its ability targets are the item's, its granted ability is not one the item has) — so no gear choice makes a lineage empty, read per item. The content loader enforces this.
  3. The lineage and its starting Blessing are hidden. The lineage is revealed the first time any of its boons is revealed (a boon's name shows its god).
  4. The three starting Blessings (decided 21 Sep 2026, D15): Greek Athena's Guard (+1 armour against weapons, +1 against spells); Norse Thor's Vigour (+4 Health); Hindu Vayu's Breath (+1 walk range). Placeholder numbers.
  5. Boons are named "<God>'s <thing>" (decided 21 Sep 2026): Apollo's Bowstring, Skadi's Hide, Agni's Crown — so a reveal names the god and therefore the lineage.
  6. Flavour direction (proposed, not rules): Greek = precision and control (Apollo range, Athena defence, Hermes movement); Norse = aggression and endurance (Thor lightning, berserk trades, Odin knowledge); Hindu = elements and transformation (Agni fire, Vayu wind movement, Indra storms).
  7. Adding a lineage is data plus art. Balance goal: every lineage viable with every kit.

Boons

Boon is the umbrella term for anything a lineage grants. Three kinds: a Blessing (a passive on the character), an Enchant (a change to one equipped item), a Sigil (a new active ability on one equipped item). Boons are drafted between rounds and last the session.

KindAttaches toWhat it can doExamples
BlessingCharacterStat change; a modifier (resist, immunity, rider); AP changeImmune to fire · +4 Health · +1 AP
EnchantOne item (by slot / kind)Change an item's numbers (range, damage, cost of its abilities); add an element to its abilities; add a modifier while equipped+1 range on bow · fire on crown · shots cost 1
SigilOne item (by slot / kind)Add a new ability to the itemTriple Shot on gun · Blink on boots · Cleave on blade

Rules

  1. A boon has: id, name, kind, lineage, requires (a slot and optionally an item kind; forbidden on a Blessing, required on the other two), effects[], stackable (default false), exclusive[], description, icon.
  2. Effect vocabulary (decided 21 Sep 2026; closed list, one handler each in Core): stat (key, amount — Blessing only), modifier (id, attached to the unit — Blessing or Enchant), abilityOverride (target = the Enchant's slot or one ability id, a Blessing's target = an innate ability id; field one of range, minRange, damage, cost, apex, climb, jumpHeight with an additive amount, plus the skeletons hits, trajectory, lineOfSight), addElement and addTag (the Enchant's slot: every attack the item grants), grantAbility (Sigil only: the slot and an ability id). Loading fails closed on an unknown type or a field that does not belong to the type. New effect types are design decisions.
  3. stackable (decided 21 Sep 2026): a boon may be drafted again while owned only when every effect is a stat or an abilityOverride. exclusive[] (decided 21 Sep 2026, D18): group tags; the draft never offers a boon sharing a group with an owned one. Two element Enchants on one slot share a group.
  4. Boons are hidden: a Blessing reveals when its modifier or stat changes a result (an hp or AP Blessing at round start); an Enchant reveals on the observation that contradicts what the opponent knows (the table in Hidden information); a Sigil reveals when its ability is used. Revealing a boon reveals its whole definition — name, god, every effect — and the first boon of a lineage reveals the lineage.
  5. The starting Blessing from the lineage is an ordinary Blessing, granted at select instead of drafted.
  6. Boons never remove abilities or items. No cap at best of 3 (decided 21 Sep 2026): at most two drafted and one starting; a longer series is when a cap or tiering gets designed.

Blessing (boon kind)

A passive on the character. Examples from the notebook: immune to fire damage, increased max health. Implemented as stat effects, unit-attached modifiers, or an override on the innate walk.

  3. Hidden until it changes a result; stat Blessings on visible stats (hp, AP) are revealed at round start.
  4. Self trade-offs are allowed (decided 21 Sep 2026, D8): a Blessing may lower the owner's own stat ("+2 Strength, −2 Health"), never an enemy's, and the total is floored by rules.boons.floors (Stats rule 3).

Enchant (boon kind)

A property change on one equipped item. Examples from the notebook: increase range on bow; add fire damage on crown (adds a fire rider to every spell). The notebook called this kind "boon"; renamed to avoid clashing with the umbrella term.

  1. requires names a slot and optionally an item kind; the draft never offers an Enchant the player cannot attach.
  2. An Enchant may override numbers of the item's abilities (range, minimum range, damage, cost, apex; on boots the movement's range, climb and jump height), add an element or a tag to every attack of the item, or attach a modifier while the item is equipped (always, since gear is locked).
  3. An override's target is the slot or one named ability (decided 21 Sep 2026, D6). A slot means every ability the item grants, including a Sigil's ability drafted later; a named ability means that one, and it must be one an item of that slot (or a Sigil of the same lineage on that slot) grants.
  4. Overrides are additive integers; the ability definition file is never edited. A field with no meaning on one of the item's abilities (an apex on a straight shot) is ignored for that ability.
  5. Cost never drops below rules.boons.minCost, 1 at launch (decided 21 Sep 2026, D7): nothing is ever free. Range never drops below 1; the minimum range stays inside the band.
Partial. In code (22 Sep 2026): every kind of override above, elements, tags, modifiers, the floors, the reveal by observation. The skeletons hits, trajectory and lineOfSight parse and fail closed. Presentation (the changed number on the button) is part 2.

Sigil (boon kind)

A new active ability inscribed on one equipped item. Examples from the notebook: triple shot on gun, teleport on boots. The notebook called this kind "gift"; renamed Sigil (a mark on the item that unlocks a power).

  1. requires names a slot and optionally an item kind (Triple Shot needs a gun). A Sigil's only effects are grantAbility on that slot.
  2. The granted ability is an ordinary ability file; it appears in the HUD section of its category and in examine under the item, after the item's own abilities. A weapon Sigil grants weapon attacks, a crown Sigil spells (the slot's lane rule); the granted ability must not be innate, and the draft never offers a Sigil granting an ability the player already has.
  3. Hidden until first used, like every ability; using it reveals the Sigil and its lineage. The item is the ability's public source: an extra "?" under the crown is a fair tell.
Partial. In code (22 Sep 2026): Sigils granting attacks of an existing shape and movement modes; six ship. A multi-hit Sigil is a skeleton (Attacks); cones, lines, areas and non-damage spells are design questions first. Presentation is part 2.

Information

Hidden information and reveal

The client mirror shipped 17 Sep 2026 (ADR-026): the client rebuilds a knowledge-limited MatchState from the PlayerView on every message and asks it every preview question, so it can only ever reason with what the server chose to send, and a hidden entry keeps its "?" slot rather than quietly becoming a certainty. A test sweeps a whole match to check no hidden damage line ever arrives before its reveal.

The server holds the truth; each client only ever receives a PlayerView. What the opponent knows at the start of round 1 and what becomes known over the session:

Rules

  1. Revealed sets are per viewer, live in state, persist for the whole session (ADR-018).
  2. Reveal events precede the event that needed them, so a client updates atomically.
  3. The damage preview is computed with the attacker's knowledge; hidden enemy modifiers count as "?" lines. Preview and actual share one function (ADR-017).
  4. A passive hidden modifier that has no visible effect produces no event for the opponent.
  5. The examine panel shows unknown abilities as "?" slots under each item, so the count of abilities per item is public while their identity is not. A later Sigil therefore shows as an extra "?", which is a fair tell. The count of drafted boons is public the same way.
  6. The client mirror. Online, the client's only rules object is a MatchState rebuilt from its own PlayerView on every server message (ADR-026). It answers previews with exactly the viewer's knowledge (hidden enemy modifiers and boons survive as a "?" count), can refuse an illegal command before it is sent, and cannot apply commands. Nothing the server never sent can be in it.
  7. An Enchant reveals on the observation that contradicts what the opponent knows (decided 21 Sep 2026, D11). Before the action is applied, the ability as the opponent knows it is compared with the ability as it is:
    ObservationWhat it reveals
    Aim or movement: a target or destination the known version could not reach (range, minimum range, apex, climb, jump height)every boon overriding an aiming or movement field of that ability
    Cost: the AP spent differs from the known costthe boons overriding that ability's cost
    Element or tag: the attack carries one the known version does not (visible in flight)the boons that added it

Determinism and replays

Same seed + same commands = same state on server, client and tests. All randomness (draft offers, first mover, bots) goes through the seeded Rng. No floats in rules, no clock in the command log (timeouts are commands).

  1. Enables replays, spectating, balance simulations with bots, and cheap server validation.
  2. Content parity is checked by a SHA-256 over canonical JSON before a match.

Meta

Bots

Bots exist for practice, balance simulation and filling a queue. RandomBot picks uniformly over legal commands. A greedy bot (maximise expected damage, avoid death) is the next step for balance runs.

Decided 17 Sep 2026, shipped the same day: Play vs bot runs on the server. The lobby button opens a room with the bot in seat 1 through the same wire as a human match, so one client code path serves both; the bot never resigns and never times out. The bot wears the flintlock / blink preset. The client-side practice mode stays as an Editor fallback — opening the Arena scene directly still plays a whole local game.

Decided 22 Sep 2026: the bot prays to a lineage drawn at random from the three with a seed the room takes at creation (so every lineage gets seen and a log line names it), drafts the first offer after its usual think delay, and plays the full best-of-3 (P5, P6). Its lineage's starting Blessing is what makes reveals happen online; the two dev passives it used to carry (ward-of-feathers, stone-skin) retired with part 2, and a test that wants a known reveal fixes the lineage through Mimas:BotLineageId.

Online: matchmaking, ratings, accounts

The server holds the truth for every online match; a client only ever receives its own PlayerView and the events filtered for it. M2 ships the smallest online game that is honest: a guest name, a room you reach by a four-letter code, a server bot, one flat turn clock, resign, and a reconnect grace.

Rules (M2 scope, decided 17 Sep 2026)

  1. Guest auth: a name only. The server issues a resumable token; the client keeps it in browser storage so a page reload rejoins. Accounts later (M5).
  2. Room codes (decided 17 Sep 2026, OPT-0001). Create a room and you get a four-letter code from an alphabet with no I, O, 0 or 1, and a link that carries it; a friend joins by pasting either. Codes are case-insensitive. Gear is chosen in the room, after you can see who you are playing, and the match starts when both seats press Ready. A matchmaking queue is M5, with ratings: four friends in two arranged pairs are not a matchmaking problem, and a queue would pair them in the order they clicked.
  3. Play vs bot opens a room on the server against RandomBot at once, through the same wire as a human match (see Bots).
  4. Clock: see Time controls. The server is the timekeeper and ends a turn itself by submitting EndTurnCommand(Timeout).
  5. Reconnect: a dropped seat is kept for 60 s (rules.clock.reconnectGraceMs); the clock keeps running; the opponent sees a countdown; a return within the grace replays the current PlayerView; no return = forfeit (see Win conditions).
  6. Resign is a command, legal at any time while the match runs, never chosen by a bot. A forfeit is the same command submitted by the server with reason disconnect, so a replay of the command list reproduces the match.
  7. Client mirror: the client rebuilds a knowledge-limited MatchState from the PlayerView attached to every server message and asks it every preview question; it never applies commands (ADR-026, see Hidden information).
  8. Lobby is its own scene; see Presentation.
  9. Rematch (decided 21 Sep 2026): the room outlives the match. After the result both seats are back in the same room, same code, Ready reset, gear and lineage editable; both pressing Ready starts the next series. Within a series the rounds follow each other with the draft between them, and the room goes back to Waiting only when the series ends. A seat whose connection is gone at the result is freed, so a friend can rejoin by code; a room with no human closes. No offer/accept: the room is the offer.
  10. The session on the wire (decided 22 Sep 2026, P3): session events travel in the same event list as a round's, a session block sits beside the view on every match message, a draft pick is a command, and every round begins with a match.start (ADR-036). Between rounds there is no view and the board the client already has is dimmed under the draft.

Later (proposed)

  • Rating: Glicko-2 per time control, updated per session, not per round; the queue window widens with wait.
  • Accounts, presets stored server-side, spectating.
Implemented for the M2 scope (17 Sep 2026): guest auth with a resumable token, rooms by code, the server bot, the 30 s server-authoritative turn with its lag grace, resign, the 60 s reconnect grace and forfeit, and the client mirror. Targeting

Arming an attack turns the board into an answer to one question: what happens if I shoot there? The rules already know (Attacks, Line of sight, Trajectories); targeting is that answer drawn. Every part of it is local presentation — the cursor, the armed ability and the hero's facing never enter Core or the wire, so they tell the opponent nothing about what a player is considering.

  • Range is two true circles. Range is Euclidean, so the band really is an annulus and drawing it as one is honest rather than decorative. The circles are distance math in the tile shader: each fragment measures its own world distance to the attacker, lights the band and dims the rest, which makes the circles bend over steps and plateaus for free. No decal (URP's Decal Projector does not render on WebGL2, Unity IN-90245) and no ring mesh to seam at a height change.
  • The path preview has four states, and the state is the whole message: clear — a dashed green path flowing towards the target with a ring on the point it will hit; blocked — red, stopping where the shot stops, an X on the blocker, the blocking tile tinted (and the body standing on it, which is otherwise hiding its own tile from above), and the reason named as the tooltip's first line ("No line of sight" / "Trajectory blocked"). The hex the rules blame is often beside the drawn line rather than on it, because a grazing ray is blocked if either flanking hex blocks (rule 5) — so saying which hex it was is the difference between a rule and a mystery; out of range — grey, with an "Out of range" tag beside the cursor; cannot be hit — grey with a dimmed ring, for a wall. An empty tile gets the grey path and no words: there is nothing to say.
  • A refused shot still shows its damage. The player is choosing between shots, and "this one is worth moving for" is the decision. The number comes from the same calculator the rules resolve with (Damage, ADR-017); the target's bar shows no ghost, because nothing is going to happen.
  • Snap priority: a living enemy's aim point, else a prop's hit mark, else the hovered tile centre at aim height. Hovering any part of a body selects that body, so the cursor never has to find a hex behind a hero's feet. The drawn line ends exactly where the rule's ray ends.
  • The projectile flies the previewed curve. Preview and playback are handed the same evaluator, so what the player was shown is what flies; the hit lands — bar and flyover — on impact, not when the event arrives.
  • Facing turns the hero towards whatever the cursor snapped to while an attack is armed, and towards the nearest living enemy otherwise. A hero with no enemy left keeps the yaw it had.
  • Heights are one number. The board converts Core's body units to world units once, from rules.heights.unitsPerLevel, and every aim point, prop box and arc is placed with it. A hero's aim point is where the rules say it is, not where it looks right.

Props render as code-built hex prisms the size of the hex they block, with a hit-mark band at their aim height, and the projectile as a flat sphere, until there is art. They were narrower boxes until 21 Sep 2026, which made a shot look legal past a pillar the rules block with the whole hex column. Implemented 16 Sep 2026; ADR-025.
