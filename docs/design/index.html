How to use this document

This page is the single source of truth for what Mimas is. Nothing gets built that is not written here first. Code that disagrees with this page is a bug in the code or a missing decision here, never a silent new rule.

The contract

  1. Design first. Before any Core, Server or Client work, the concept it touches must exist here with status decided or proposed. If it does not, add it (as proposed) and get it confirmed, or log a question in the section's Open questions block.
  2. Every concept has two statuses. Design: decided (Rohan confirmed), proposed (a default written by Claude, not yet confirmed), open (no default is safe), superseded (replaced; kept for history). Code: in code, partial, not started, drift (the code implements something different from this page).
  3. Drift is loud. When a section carries drift, the section says exactly what the code does instead and which change is planned. The drift register is generated from these flags.
  4. Link, do not repeat. A rule lives in one section. Other sections link to it with #anchor. Backlinks ("Referenced by") are computed when the page loads, so cross references never go stale.
  5. Numbers are data. Balance values quoted here are the current JSON values and may change without a design decision. Formulas, slots, visibility rules and vocabulary may not.
  6. Architecture goes to the ADR log. Design decisions are recorded here in the decision log; architectural ones also get an ADR in docs/decisions.md. Data schemas are detailed in docs/data.md; this page only sketches them.
  7. Anchors are stable. Commit messages, ADRs and CLAUDE.md cite sections as design/index.html#equipment. Never rename an anchor; add a new section and mark the old one superseded.

Editing checklist (for Claude Code and Rohan)

  • New concept: copy any <section class="concept">, give it a unique id, data-design, data-impl, data-title, place it under the right group.
  • Changed rule: edit the rule, add a line to the changelog, update the statuses. If code now disagrees, set data-impl="drift" and add a .drift-note.
  • Answered question: delete the <li> from the section's open questions, write the answer into the rules, log it in the decision log.
  • Status vocabulary is closed. Do not invent a fifth design status.

Vision and pillars

A browser-based 1v1 turn-based tactics duel on hex maps. A Baldur's Gate 3 fight distilled into a competitive, chess-like ladder game with hidden information and TFT-style power drafting. No story, pure play.

Reference games

Baldur's Gate 3 (tactical feel, camera), chess (time controls, ladder, clean information model), Teamfight Tactics (augment drafting), Hades (god-granted boon pools), Into the Breach (deterministic, readable combat).

Non-goals

  • No campaign, no dialogue, no lore text beyond one line per item or boon.
  • No random damage. See Damage.
  • No more than one hero per player at launch. The model is multi-unit ready but summons are a later boon idea.

Loop

Session

A session is one matchmade encounter between two players. It is a best-of-X series of rounds, each on the next map of the ladder, with a draft between rounds. The build (gear, lineage, boons) carries forward for the whole session.

Rules

  1. A session starts after matchmaking pairs two players on the same time control.
  2. Both players go through character select before round 1. Selection is simultaneous and private.
  3. Rounds are played on ladder maps in order: round 1 on ladder position 1, round 2 on position 2, and so on.
  4. The session ends when one player has won the majority of rounds (best of 3 at launch, so first to 2). See Win conditions.
  5. After every round except the last, both players draft one boon.
  6. Everything learned through reveals stays revealed for the rest of the session.
  7. A player who leaves and does not reconnect within the grace period forfeits the session (see Online).
Drift. Code has MatchState for one round and no series wrapper. Mimas.Core.Match is one round; a Session (series score, ladder index, per-player build, revealed sets that outlive a round) is not started. Planned for M3.

Depends on

  • Round, Draft, Maps, Character select

Open questions

  • Best of 3 vs best of 5 as the default, and whether the count depends on the time control (bullet = single round?).
  • Whether the ladder is strictly ordered or the server picks from a pool per ladder position.

Round

One map, played in alternating turns until one hero dies. The round winner takes a series point.

Rules

  1. Each player has exactly one hero, spawned on their map spawn (p1 / p2) at full health.
  2. Who moves first: round 1 by a seeded coin flip; then the loser of the previous round moves first (proposed).
  3. The round ends the moment a hero reaches 0 health (by damage or environment).
  4. Between rounds, health, AP and one-round states reset; gear, lineage, boons and revealed knowledge persist.
  5. The round clock (see time controls) restarts per round. A flag fall loses the round, not the session (proposed).

Open questions

  • Confirm first-mover rule: coin flip then loser-first, or alternate.
  • Does the chess clock reset per round, or is one clock shared across the whole session?
  • Flag fall = lose round or lose session?

Source: design v0.1 win conditions; ADR-015.

Character select

Before round 1, each player builds their hero in two steps, in this order: 1. pick gear (one item for each of weapon, armour, crown, boots), 2. pick a divine lineage to pray to. Simultaneous, private, on a timer.

Rules

  1. Step 1, gear: one item per slot from the full item catalogue. All four slots are mandatory. There are no classes; "warrior" and "mage" survive only as suggested presets in the UI.
  2. Step 2, lineage: one of Greek, Norse, Hindu (Lineage). Shown after gear so the player can pick a god that suits the kit (the lineage's boon pool is filtered by owned gear).
  3. The choice is locked for the session. Gear only changes through Enchants and Sigils.
  4. Selection timer: 60 s (proposed). Timing out picks the last preset the player used, or the default preset.
  5. The opponent sees your gear at round start (public) but never your lineage or starting Blessing until revealed.

  • Is the whole item catalogue always available, or is there any unlock or ban/pick phase?

Draft (between rounds)

After every round except the last, each player is offered three boons from their lineage's pool and keeps one. The pick is private and simultaneous.

Rules

  1. Offers are drawn with the session seeded RNG, so a replay reproduces them.
  2. Only boons the player can use are offered: an Enchant or Sigil whose requires does not match the player's gear is excluded; a boon already owned is excluded unless it declares stackable.
  3. Offers are one of each kind when possible (one Blessing, one Enchant, one Sigil, proposed); otherwise filled from what remains.
  4. Draft timer: 20 s (proposed). Timeout picks the first offer.
  5. The pick is hidden. The opponent sees only that a pick was made.
  6. Picks apply immediately and last for the session.

Open questions

  • Comeback mechanic: does the round loser get a better offer (a tier up, or four options), or is the draft symmetric?
  • Do boons have tiers/rarity (TFT silver/gold/prismatic) and does the tier depend on the round number?
  • Is there a reroll?

Source: pillar 7; notebook 16 Sep 2026; round-2 answer "starting passive + lineage pool".

Turns and action points

Players alternate. On your turn your hero has 3 AP; every ability has a flat AP cost and can be used as often as AP allows. Unspent AP is lost. End Turn passes early; the clock cap passes for you.

Rules

  1. Alternating turns, one actor at a time (ADR-015). No simultaneous planning, no initiative stat.
  2. AP refreshes to the unit's ap stat at the start of its owner's turn (ADR-016). AP lives on the unit, not the player, so summons can arrive later.
  3. An ability costs its cost (default 1, may be 0). No per-turn use limits other than AP; cheap repeatable attacks are a data balance lever.
  4. Legal actions are enumerated by one function (EnumerateLegal) that the HUD, the server and bots all use, so they cannot disagree (ADR-018).
  5. Reaching the per-turn clock cap with no action = skip. The server submits EndTurnCommand(Timeout) so replays need no clock.
  6. An idle skip gives the next turn a short fuse (idle penalty) that resets the moment the player acts.
  7. Boons may change ap or an ability's cost (e.g. a Blessing "+1 AP", an Enchant "Shot costs 1"). See Stats.

Depends on

  • Time controls, Abilities

Source: ADR-015, ADR-016, ADR-018.

Time controls and clock

Game modes are chess-style time controls. Each player has a bank, an increment, and a per-turn cap. Presentation follows Hearthstone: no visible numbers, a rope in the last seconds.

Current values in timecontrols.json; balance data, not design.

Rules

  1. The server is the timekeeper; the client predicts and displays.
  2. The rope appears for the final seconds of a turn and burns down; the bank is never shown as digits in the HUD (examine may show it).
  3. Idle penalty: see Turns.
  4. Draft and character select timers are separate from the game clock.

Open questions

Win conditions

  1. Round: the opponent's hero reaches 0 health, by damage or by the environment (tile effects, later).
  2. Session: majority of rounds (best of X, see Session).
  3. Resign concedes the session. Flag fall: see open question.
  4. Simultaneous death (both heroes at 0 in the same resolution, possible once environment damage exists): the active player loses (proposed, punishes the reckless actor).
Partial. Elimination win exists (MatchEndedEvent); resign, series score and simultaneous death are not in code.

Open questions

  • Confirm the simultaneous-death rule or allow a drawn round.
Board

Board: hex tiles, terrain, height

The board is any set of hex tiles (axial coordinates, cube math). Each tile has a terrain, an integer height and optionally a modifier. Shape is data: rings, boards, arenas are all just hex lists.

Rules

  1. Terrain (terrains.json): walkable, moveCost, optional modifiers[] granted to whoever stands on it. Current: grass (walkable, 1), stone (blocking).
  2. Height is a rules value: walking may rise at most maxClimb per step; a jump is blocked by anything more than jumpHeight above the origin; line of sight is blocked by tiles taller than both endpoints. Descending is never limited.
  3. High ground: attacking from a higher tile adds a public flat bonus (global modifier high-ground, currently +2). See Modifiers.
  4. Occupancy: one living unit per tile; dead units occupy nothing.
  5. All geometry is integer-exact (HexLine, ADR-013) so server and client agree bit for bit.

Line of sight

Every attack, including melee, requires a clear line of sight to its target. Teleports may require it as a balance lever. Sight follows the exact hex line and is blocked by unwalkable tiles and by tiles taller than both endpoints.

  1. A grazing line (through a hex edge or corner) is blocked if either flanking tile blocks (supercover). Line(a,b) equals Line(b,a).
  2. Units do not block sight (proposed; only one enemy unit exists, so it is moot at launch).

Open questions

  • Should units block sight once summons or obstacles exist?

Source: ADR-013; design v0.1 targeting decision.

Maps and the ladder

Maps are JSON hex lists with a declared symmetry, two spawns and a ladder position. Every shipped map is validated at boot: symmetric with matching terrain, spawns walkable and at maximal distance, all walkable tiles connected.

  1. Symmetry: rotational-180 implemented; mirror-q reserved.
  2. Spawns are opposite each other at maximum walkable distance (pillar 14).
  3. Ladder: ladderPosition orders maps; lower positions are smaller and simpler, higher ones add height, pillars and (later) tile effects. Current: board-3 (position 1?), arena-4 (position 3).
  4. Heights must be symmetric too (enforced by test only; loader check pending).

Open questions

  • How many maps per ladder position for variety, and whether players see the next map before drafting.

Source: pillars 3, 14; ADR-014; docs/data.md.

Tile effects and pickups

Pillar 4 promises tile effects: bonus pickups, hazards, terrain modifiers. Terrain modifiers exist (a terrain or a hex can grant a modifier to whoever stands on it). Pickups and hazards are not designed.

The movement model already separates Path (what to animate) from EnteredTiles (what tile effects fire for: every tile of a walk, only the destination of a jump or blink), so an OnEnter hook can be added without touching resolvers (ADR-012).

Open questions

  • What can a pickup be: AP, health, a one-round boon, a charge? Does it respawn?
  • Hazards: damage on enter, damage per turn standing, knockback into holes (environment kills)?
  • Are tile effects always public? (Proposed: yes; hidden information lives on characters, not on the board.)
Character

Character

A player's hero is defined by three things and nothing else: gear (four items), a divine lineage, and the boons drafted during the session. There are no classes.

Rules

  1. Derived stats = base values (rules.json) + sum of item stats + Blessing and Enchant stat effects.
  2. Derived ability list = innate movement (walk) + abilities of each equipped item + abilities added by Sigils. Order in the HUD: movement, weapon, spell.
  3. Derived modifier list = Blessings' modifiers + Enchants' modifiers + whatever the tile grants + global rules.
  4. One hero per player. The unit model stays multi-unit ready (per-unit ids and AP).
  5. Nothing about the character is random. Same picks = same character.
Drift. Code defines characters by classes/*.json (warrior, mage) that own abilities and stats directly. Plan: replace classes/ with items/ + lineages/ and a Loadout in MatchSetup; warrior/mage become UI presets. Class stats table in docs/data.md will be superseded.

Stats

Six numbers describe a hero. Display names on the left, engine keys on the right. All integers; all public knowledge except where a hidden boon changed them.

Rules

  1. Keys follow power.<lane> / defense.<lane> for the two lanes in rules.damageTypes (weapon, spell). This keeps the existing generic stat table; only the lane list and display names change.
  2. Every hero has the same base stats, in rules.json baseStats (current placeholders: hp 20, ap 3, Strength 1, Magic 1, armour 0/0). Items are pure additions, so the stat block is a sum. New stats are JSON only.
  3. No item carries a negative stat at launch (the loader rejects them). hp is at least 1, ap at least 0. Negative effects, if ever, come from boons and need a floor rule first.
  4. Enemy stats are public because gear is public. A hidden Blessing that changed a stat is revealed the first time the changed stat alters a result (for hp: at round start, since max health is visible on the bar; so hp Blessings are effectively public).
Drift. Code lanes are melee / ranged / magic (rules.json) and stats sit on classes. Migration: damageTypes becomes ["weapon","spell"], attack damageType values are remapped (jab, strike, bow shots = weapon; fire-bolt = spell), stats move to items. Display names are a client concern.

Equipment (gear)

Four slots, one item each, all mandatory, locked for the session: Weapon, Crown, Boots, Armour. Items are the only source of stats and abilities besides the lineage.

Rules

  1. An item has: id, slot, kind (bow, gun, blade, … used by boons' requires), stats (any stat keys), abilities[] (ability ids it grants), tags[] (matched by modifiers), one-line description, presentation keys (model, icon).
  2. Item identity is public: the opponent sees the item name and its innate stats. Its ability list is not shown until each ability is used.
  3. Items never change identity during a session. Enchants attach to an item and alter its numbers or add tags; Sigils add abilities to it.
  4. Slots are fixed at four. New item kinds are data; new slots are a design decision.
  5. Items are pure additions: no negative stats, no set bonuses, no anti-synergies. Synergy comes from boons.
  6. Every base weapon and every base crown carries exactly two abilities. Boots carry one movement mode. Armour carries none. (Authoring convention on shipped content, enforced by a repo-data test; the loader itself only requires a weapon to have an attack.)
  7. Launch catalogue (16 Sep 2026): weapons bow and gun; one crown; boots jump and teleport; one armour. Blade (melee) is deferred, not rejected.

The weapon grants the hero's two weapon-lane attacks and some Strength. Every weapon has a minimum and a maximum range. Kinds at launch: bow and gun. Both hit adjacent enemies; the gun reaches further, the bow hits slightly harder.

Crown slot

"This is where spells come from and are used." The crown grants the hero's spell-lane attacks and Magic. A crown may also carry an innate element.

  1. Every base crown lists exactly two spells. More spells arrive through Sigils.
  2. An Enchant on the crown can add an element to every spell it grants ("fire on crown" = all crown spells are tagged fire and gain a fire rider).
  3. Spells are attacks in the spell lane; they may ignore some targeting rules by data (e.g. minRange), but always need line of sight.
Drift. Fire Bolt is a mage class ability with lane magic. Becomes a crown ability with lane spell and element: fire.

Open questions

  • Can crowns grant non-damage spells (heal, shield, slow)? Needs an effect vocabulary beyond damage. Proposed: not at launch.

Source: notebook page 1 (Crown).

Boots slot

"Gives different kinds of movement." Every hero can walk innately (1 hex per AP, climb 1); boots grant one extra movement mode (jump, teleport, later fly or dash) and may alter walk parameters.

  1. Walk is innate and never removed; it is listed in rules.innateAbilities rather than on any item.
  2. Boots grant abilities[] (movement kind) and may set walkRange / maxClimb overrides via stats (proposed keys walk.range, walk.climb).
  3. Sigils can add a second movement mode to boots ("teleport on boots").
Drift. Jump and teleport are class abilities; walk is granted by classes listing move. Boots do not exist.

Source: notebook page 1 (Boots).

Armour slot

Armour negates damage with two separate numbers: defense.weapon and defense.spell. It is also the main source of Health. Plate can be great against weapons and weak against spells; robes the reverse.

  1. Defence is flat and subtractive per hit (see Damage). It never reduces a hit below 0.
  2. Elemental resistances and immunities are not armour numbers; they are modifiers from Blessings or Enchants on the armour.
  3. Armour has no HP pool of its own (ablative armour rejected).
Drift. Defence values sit on classes as defense.melee/ranged/magic.

Source: notebook page 1 (Armour negates damage); round-2 answer "separate weapon and spell reduction".

Combat

Abilities

An ability is anything a unit spends AP on. Two types exist: movement and attack. Every ability is data (abilities/*.json) with a flat AP cost, a HUD category (movement, weapon, spell) and an icon. Abilities come from gear and sigils, never from the character directly.

  1. Fields shared by all: id, type, name, description, icon, category, cost (default 1).
  2. An ability's owner is the item that grants it (or the innate list). The HUD groups by category; the examine panel groups by item.
  3. Abilities are hidden from the opponent until first used, even when the granting item is public.
  4. Enchants may alter an ability's numbers (range, damage, cost) through the item they attach to; the ability definition itself is immutable.
Partial. Abilities load and resolve; the "owner item" link and enchant overrides do not exist (abilities are referenced straight from classes).

Depends on

  • Turns and AP, Equipment, Sigil

Source: ADR-012, ADR-016; docs/data.md.

Movement

Movement kinds differ in geometry; everything else is a data table. Modes: walk (path search, terrain cost, climb limit, cannot cross units), jump (straight line, arc clearance by height), teleport (point pick, optionally needs sight). Fly is a walk whose cost table says everything costs 1 plus ignoreHeight.

  1. Destination must exist, be enterable and unoccupied. Origin is never a destination.
  2. Walk refuses to cross occupied tiles; jump and teleport cross anything, including holes, and enter only their destination.
  3. terrainCosts per ability overrides the terrain catalogue (an integer makes even stone enterable; null makes even grass impassable).
  4. A move produces a MovePlan: Path to animate and EnteredTiles for tile effects.
  5. New modes are one resolver class plus one JSON; unknown modes fail closed.

Source: pillar 12; ADR-012; docs/data.md "Movement abilities".

Attacks

An attack targets one living enemy unit inside a minRange..range band with clear line of sight, always, even at range 1. It declares its lane (weapon or spell), a flat base damage, optional element and tags.

{ "version": 1, "id": "fire-bolt", "name": "Fire Bolt", "type": "attack", "category": "spell", "cost": 2,
  "attack": { "damage": 6, "damageType": "spell", "range": 3, "minRange": 1, "element": "fire" },
  "tags": ["bolt"] }
  1. category is weapon or spell and must match the lane (an attack granted by a crown is a spell; by a weapon, a weapon). HUD only reads category; rules read the lane.
  2. Targeting and legality come from one function used by HUD, server and bots.
  3. Multi-target shapes (cone, line, area) are not designed; Sigils like Triple Shot will need a shape or a multi-hit count. See open question.
Drift. Lane values in code are melee / ranged / magic; there is no element field. See Stats for the migration.

Open questions

  • Multi-hit and area attacks (Triple Shot, Cleave): repeated single resolution vs a shape. Proposed: hits: 3 repeats the single-target resolution; shapes later.

Source: ADR-017; design v0.1 targeting decision.

Damage

Deterministic. No dice, no hit chance. Two lanes, weapon and spell; each lane has a power stat (Strength or Magic) and an armour defence. Elements and everything else are flat modifiers on top.

damage = max(0,  base
               + power.<lane>            (attacker: Strength or Magic)
               - defense.<lane>          (target's armour, weapon or spell)
               + Σ flat modifiers )      (elements, high ground, blessings, enchants, terrain)
  1. The result is a fixed-order list of signed lines (base, power, defence, then modifiers grouped attacker unit / attacker tile / globals, target unit / target tile / globals, sorted by id) plus the total. This is what the tooltip shows.
  2. Preview and actual are the same function. The preview uses the attacker's knowledge (hidden enemy modifiers dropped and counted as "?"); the server resolves with full knowledge. When they differ, the modifier that caused it is revealed.
  3. Immunity (from a Blessing) is a modifier whose effect nullify sets the total to 0 after everything else. Shown as one line "Immune (fire)".
  4. Percentages are not allowed. If ever needed they are computed in integer basis points, never floats.
  5. Enemy health is fully visible (pillar 8 surprise lives in abilities and modifiers, not in the health bar).
Drift. Formula and calculator exist exactly like this, but lanes are melee/ranged/magic and there is no nullify effect.

Depends on

  • Stats, Modifiers, Elements, Hidden information

Source: ADR-017; round-1 answer "everything is either WP or SP".

Elements and modifier classes

An element (fire, frost, lightning, …) is a modifier class: a tag an attack carries that resistances, immunities and riders match on. It is not a third damage lane. Other modifier classes (e.g. bleed, holy) can be added the same way later.

  1. rules.json declares elements[]. An attack may carry at most one innate element; an Enchant can add one to every attack of an item.
  2. A rider is a dealDamage modifier with when.elements and a positive effect.damage ("+2 fire").
  3. A resistance is a takeDamage modifier with when.elements and a negative effect.damage; an immunity uses effect.nullify.
  4. Elements have no rock-paper-scissors table at launch (fire beats frost etc.). Any such interaction is a modifier in data.
  5. Elements are shown as an icon on the ability button and as a line in the damage tooltip.

Open questions

  • Launch element list. Proposed: fire, frost, lightning (one per lineage flavour is tempting but lineages should share elements).
  • Do elements ever apply a status (burn per turn, frost slows)? Needs a status system; not at launch.

Source: notebook page 2 (Damage types: weapon, spell, elemental); round-1 answer "elemental has its own class (fire, frost, etc), other kinds of damage modifiers later".

Modifiers

A modifier is one trigger, a conjunction of conditions, and one flat effect. Who owns it is the attachment, never the file: a unit (via Blessing or Enchant), a terrain, a map hex, or the global rules.

{ "version": 1, "id": "agni-fire", "name": "Agni's Fire", "trigger": "dealDamage",
  "when": { "damageTypes": ["spell"], "elements": ["fire"] }, "effect": { "damage": 2 }, "visibility": "hidden" }
FieldValues
triggerdealDamage (attacker side) · takeDamage (target side)
whendamageTypes[] (lane) · tags[] · elements[] (new) · heightAdvantage · itemKinds[] (new: attack granted by a bow) · all must hold
effectdamage (signed flat) · nullify (new, immunity) · more effect keys are design decisions
visibilitypublic (tiles, globals) · hidden (boons) until it changes a result
  1. The same id twice on one unit does not stack.
  2. Order never matters for the total (all flat, then floor, then nullify).
  3. Modifiers never change AP, range or stats; those are Enchant stat effects. Modifiers only touch damage results.
Partial. Trigger, damageTypes, tags, heightAdvantage, effect.damage, visibility and reveal exist. elements, itemKinds, nullify are new.

Divine

Divine lineage

At character select, after picking gear, the player chooses the divine lineage they pray to. Launch lineages: Greek, Norse, Hindu. A lineage grants one fixed starting Blessing immediately and defines the pool of boons offered in every draft. Lineages shape a build; they do not lock a playstyle.

  1. Each lineage has: id, name, startingBlessing (a Blessing id), pool[] (boon ids), one-line flavour, presentation keys.
  2. The pool must contain all three boon kinds and cover every item kind at least once, so no gear choice makes a lineage empty. The content loader enforces this.
  3. The lineage and its starting Blessing are hidden. The lineage is revealed the first time any of its boons is revealed (a boon's name shows its god).
  4. Flavour direction (proposed, not rules): Greek = precision and control (Apollo range, Athena defence, Hermes movement); Norse = aggression and endurance (Thor lightning, berserk trades, Odin knowledge); Hindu = elements and transformation (Agni fire, Vayu wind movement, Indra storms).
  5. Adding a lineage is data plus art. Balance goal: every lineage viable with every kit.

Data (proposed, lineages/*.json)

Boons

Boon is the umbrella term for anything a lineage grants. Three kinds: a Blessing (a passive on the character), an Enchant (a change to one equipped item), a Sigil (a new active ability on one equipped item). Boons are drafted between rounds and last the session.

KindAttaches toWhat it can doExamples
BlessingCharacterStat change; a modifier (resist, immunity, rider); AP changeImmune to fire · +4 Health · +1 AP
EnchantOne item (by slot / kind)Change an item's numbers (range, damage, cost of its abilities); add an element to its abilities; add a modifier while equipped+1 range on bow · fire on crown · shots cost 1
SigilOne item (by slot / kind)Add a new ability to the itemTriple Shot on gun · Blink on boots · Cleave on blade

Rules

  1. A boon has: id, name, kind, lineage, requires (slot and/or item kind; none for most Blessings), effects[], stackable (default false), description, icon.
  2. Effect vocabulary (proposed, closed list, each one handler in Core): stat (key, amount), modifier (id, attached to unit), abilityOverride (ability id or item, field, amount: range / damage / cost), addElement (item, element), grantAbility (item, ability id). New effect types are design decisions.
  3. Boons are hidden: a Blessing reveals when its modifier or stat changes a result; an Enchant reveals when an altered number is observed (a shot lands from beyond normal range, a preview differs); a Sigil reveals when its ability is used.
  4. The starting Blessing from the lineage is an ordinary Blessing, granted at select instead of drafted.
  5. Boons never remove abilities or items.

Blessing (boon kind)

A passive on the character. Examples from the notebook: immune to fire damage, increased max health. Implemented as stat effects and/or unit-attached modifiers.

  1. Requires nothing (any kit).
  2. The lineage's starting Blessing is one of these.
  3. Hidden until it changes a result; stat Blessings on visible stats (hp) are effectively public at round start.

Source: notebook page 2.

Enchant (boon kind)

A property change on one equipped item. Examples from the notebook: increase range on bow; add fire damage on crown (adds a fire rider to every spell). The notebook called this kind "boon"; renamed to avoid clashing with the umbrella term.

  1. requires names a slot and optionally an item kind; the draft never offers an Enchant the player cannot attach.
  2. An Enchant may override numbers of the item's abilities (range, damage, cost), add an element, or attach a modifier while the item is equipped (always, since gear is locked).
  3. Overrides are additive integers; the ability definition file is never edited.

Source: notebook page 2.

Sigil (boon kind)

A new active ability inscribed on one equipped item. Examples from the notebook: triple shot on gun, teleport on boots. The notebook called this kind "gift"; renamed Sigil (a mark on the item that unlocks a power).

  1. requires names a slot and usually an item kind (Triple Shot needs a gun).
  2. The granted ability is an ordinary ability file; it appears in the HUD section of its category and in examine under the item.
  3. Hidden until first used, like every ability.

Source: notebook page 2; round-2 naming answer.

Information

Hidden information and reveal

The server holds the truth; each client only ever receives a PlayerView. What the opponent knows at the start of round 1 and what becomes known over the session:

ThingAt startRevealed when
Health, position, APPublicalways
Gear (four item identities, their innate stats)Public (worn on the model)always
Derived stats (Strength, Magic, Armour)Public as far as gear explains thema hidden stat effect shows when it changes a result
Abilities (innate to items or from Sigils)Hiddenfirst use; then full definition known
Lineage and starting BlessingHiddenfirst reveal of any boon of that lineage; the Blessing when it changes a result
Drafted boonsHidden (opponent sees "picked")Blessing / Enchant: first time it changes a result or an observed number; Sigil: first use
Tile and global modifiers (high ground, terrain)Publicalways

Rules

  1. Revealed sets are per viewer, live in state, persist for the whole session (ADR-018).
  2. Reveal events precede the event that needed them, so a client updates atomically.
  3. The damage preview is computed with the attacker's knowledge; hidden enemy modifiers count as "?" lines. Preview and actual share one function (ADR-017).
  4. A passive hidden modifier that has no visible effect produces no event for the opponent.
  5. The examine panel shows unknown abilities as "?" slots under each item, so the count of abilities per item is public while their identity is not. A later Sigil therefore shows as an extra "?", which is a fair tell.
Partial. Ability and modifier reveal exist. Lineage, boon and enchant-observation reveals, and series-long persistence, are not started.

Open questions

  • Precise definition of "observed number" for Enchant reveal (range: the shot lands; cost: the AP dots differ; damage: the preview differs).

Determinism and replays

Same seed + same commands = same state on server, client and tests. All randomness (draft offers, first mover, bots) goes through the seeded Rng. No floats in rules, no clock in the command log (timeouts are commands).

  1. Enables replays, spectating, balance simulations with bots, and cheap server validation.
  2. Content parity is checked by a SHA-256 over canonical JSON before a match.

Source: CLAUDE.md golden rule 4; ADR-014, ADR-018.

Bots exist for practice, balance simulation and filling a queue. RandomBot picks uniformly over legal commands. A greedy bot (maximise expected damage, avoid death) is the next step for balance runs.

Presentation

Rules never depend on presentation. The client is a renderer of events: 3D low-poly hexes and heroes, URP on WebGL2, UI Toolkit HUD, FMOD audio, Shuriken VFX.

Camera

3D tilted view with a toggle to full top-down (BG3 "O"). Two Cinemachine cameras blended on toggle.

HUD (package D, ADR-019)

  • Thin segmented hp bar plus number under every unit, faded until hovered or an action is armed.
  • AP dots on the action bar; hovering an ability tints the dots it would spend; each button shows its cost; unaffordable buttons desaturate.
  • Action bar bottom-centre, sectioned movement / weapon / spell (item icons mark which item an ability belongs to, proposed). End Turn bottom-right. Turn owner and rope top-centre. Examine panel left.
  • Attack preview: ghosted hp delta on the target's bar plus a line-item tooltip with a "?" row for unrevealed modifiers.
  • Feedback: damage flyover; when actual differs from preview, a second line names the revealed modifier whose icon then stays on the unit.
  • Nothing is armed by default; clicking a unit with nothing armed opens examine.

Examine

Inspect any unit, tile or item: for enemies, items are shown by name with their innate stats, abilities as "?" until revealed, revealed boons listed with their lineage. For tiles: terrain, height, modifiers.

Audio and VFX

FMOD music that stays out of the way; distinct SFX per ability category and per element; VFX via Shuriken and Shader Graph (no VFX Graph on WebGL2).

Art direction

Low-poly stylised; gear must read at the tilted camera distance (silhouette per weapon kind, colour per lineage once revealed). Rules of readability come before beauty.
