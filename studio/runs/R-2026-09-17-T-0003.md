## Research

Two subagents, in parallel, before any build. Findings that changed the plan:

- **Confirmed correct, needing no change:** `DispatchMessageQueue()` called unconditionally every
  frame in `NetClient.Update()` (a documented no-op on Web, required elsewhere);
  `Application.absoluteURL` as the way to read `?room=` and `?ws=` (Unity's modern replacement for a
  `window.location.search` jslib); the server's static-file ordering and Brotli headers.
- **`http://localhost` is a secure context**, so a page on `http://localhost:7777` may open
  `ws://localhost:7777/ws` with no mixed-content block. `NetClient.ResolveUrl()` maps an `http://`
  page to `ws://<host>:7777/ws` — correct for the one-process setup, and `https://` → `wss://` is
  already right for the VPS.
- **Serving `.br` without `Content-Encoding: br` does not 404** — it hands the browser Brotli bytes as
  if they were wasm, and fails at `WebAssembly.instantiate`. Worth knowing so the error is recognised.
- Neither report found a reason to expect the build itself to fail.

### 3. The build script already existed, and it was the culprit

`MimasClient/Assets/_Game/Editor/WebBuild.cs` was already there and is what stamped
`webGLExceptionSupport: 0` into `ProjectSettings.asset` — line 32 set `WebGLExceptionSupport.None`
explicitly on every build. So Rohan's decision is a change *here*, in a plain `.cs` file, and needs no
Editor and no protected `.asset` edit.

Rewritten to:

- **`Build`** (Release) — `ExplicitlyThrownExceptionsOnly`, per Rohan.
- **`BuildDebug`** — `BuildOptions.Development` + `FullWithStacktrace`, output `Build/WebDebug`.
- Honour `-buildOutput`, which `unity build --output-path` forwards and which the executed method is
  responsible for reading. Without it the flag is silently ignored.
- Ship **enabled** scenes only. It was shipping disabled ones too, which shifts every scene index
  after a disabled row. Latent, not yet biting.
- Restore exception support in a `finally` to the **decided** value, not the previous one — otherwise a
  debug build would leave the repo recording `FullWithStacktrace`, and a release build would
  re-record `None` and quietly undo the decision. Unity writes `ProjectSettings.asset` itself, which
  is the sanctioned route.

Committed as three small commits before building, because `unity build` refuses a dirty tree without
`--allow-dirty-build`.

#### Two bugs of my own, found by this failure

1. **`EditorApplication.Exit(1)` was called from inside the `try`.** It terminates the process on the

2. **`AssetDatabase.SaveAssets()` does not write `ProjectSettings.asset`.** After the failed build the

#### What the research found about the link error

A subagent searched the Unity issue tracker, Discussions and the 6000.4.4 → 6000.4.9 release notes.

**There is no public report of `unitytls_ssl_set_client_transport_id` anywhere** — not the tracker, not
the forums, not GitHub. That is a real negative result, not a failed search. So: no issue ID, no
affected-version list, no fixed-in version, and no reason to believe a patch bump fixes it (the only
TLS fix in that range, UUM-141298 in 6000.4.8f1, is a runtime handshake regression, not a link error).

On the `com.unity.pipeline` hypothesis: the one relevant thread
([discussions.unity.com](https://discussions.unity.com/t/can-we-use-com-unity-pipeline-in-webgl-build/1731986))
says only that pipeline cannot work inside a browser sandbox; it says nothing about build or link
errors. So the hypothesis stays **plausible and unconfirmed**: a Development-Build-only HTTP listener
is exactly the shape of thing that would reference `unitytls_*` and produce an *undefined symbol*
rather than a runtime error, but nothing published settles it. Confirming it means removing
`com.unity.pipeline` and rebuilding — and `Packages/manifest.json` is protected by golden rule 7.

Also worth recording: `ERROR_ON_UNDEFINED_SYMBOLS=0` via `PlayerSettings.WebGL.emscriptenArgs` is the
common community workaround for this class of failure, and it **only defers the failure to runtime** —
wasm-ld stubs the missing import and the module traps if it is ever called. Not a fix. Not used.

#### The client connects lazily — and the harness had to learn it

Nothing reaches the socket until a button is pressed: `Awake` only resolves the URL. So an `--expect`
of `[NetClient] connected` on a passive page load can only ever time out. The harness was checking
`--expect` **before** running its steps, which made this look like a failure when it was not. Steps now
run first, then the assertion.

### 7. Three stripping bugs, which only a browser could find

The first arena had **11 console errors**. All three causes are the same shape: something that reaches
the build only at runtime, which Managed Stripping High and engine code stripping therefore cannot see.

| Symptom | Cause | Fix |
|---|---|---|
| `Can't add component because class 'CapsuleCollider' doesn't exist!` ×9, `SphereCollider` ×1 | Colliders arrive only through `GameObject.CreatePrimitive`, which adds them natively. No managed code names them, so the Physics module was dropped | `link.xml` |
| `[AimPreview] Shader 'Mimas/AimLine' not found` ×3 | Reached only by `Shader.Find` — in no scene, on no material, so not built | Always Included Shaders, from `WebBuild` |
| `NullReferenceException` | knock-on | — |

The collider one is **not cosmetic**: the body collider is what the cursor picks (design
`#presentation`), so without it nothing on the board can be clicked. A build that "looks fine" would
have been unplayable.

After the fixes: `OK — no pageerror, no console.error, no failed request`, 12.38 MB.

### 8. Magenta placeholders — a pre-existing bug the browser made visible

Units and props still drew magenta after the shader fix, so the first guess (URP's Lit being stripped)
was wrong. The evidence settles it: `Arena.unity` has `_visualMaterial: {fileID: 0}` on both
`UnitView`s — it is **null** — so `CreatePrimitive`'s built-in `Default-Material` stays on them, and
that material's shader belongs to the Built-in render pipeline, which has no valid pass under URP.

**This is not WebGL-specific.** It is true in the Editor too; the Web build simply made it impossible
to ignore. Fixed with `PlaceholderMaterial`, a shared runtime material built from
`Universal Render Pipeline/Lit`, applied by `UnitView` and `PropView` whenever nothing better is set.
Tints keep working: they are `MaterialPropertyBlock`s on `_BaseColor`, which URP/Lit has.

### 9. Persisting ProjectSettings — what actually works

`GraphicsSettings.asset` persisted on the first try; `ProjectSettings.asset` never did, through two
attempts. The difference is the mechanism, not the folder: a `SerializedObject` marks its target dirty
itself, while the static `PlayerSettings` API does not, so `AssetDatabase.SaveAssets()` has nothing to
write. `ExecuteMenuItem("File/Save Project")` is a no-op in batch mode. Now done with an explicit
`EditorUtility.SetDirty` over `Resources.FindObjectsOfTypeAll<PlayerSettings>()`.
