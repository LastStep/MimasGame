# Run: Finish M2 in the browser — rematch in the room, Mimas Web template, Copy code, blocker shown, origin check, multi-browser smoke

> Opened at the start of the session and appended to as it goes. Not written at the end.

## What is different now

**A match no longer throws you out of the room.** When it ends, both players are back in the room they
started in — same four-letter code, both seats, Ready reset — and pressing Ready again starts the next
match. Nobody types a code twice. A friend who dropped can come back by code, because their seat is
free and the room is still there.

**The page is called Mimas.** It fills the window, it is dark, it has a thin loading bar with a
percentage and its own icon, and there is no Unity splash, no Unity footer and no 960×600 box. In the
room there is now a **Copy code** button beside Copy link — the link is for a chat window, the code is
for a phone call. In a match, a refused shot says what refused it: the hex the rules blamed is tinted,
and so is the wall or pillar standing on it. Pillars and walls are drawn the size of the hex they
actually block, instead of boxes at 62 % of it, which is what made shots look legal when they were not.

On the server, in production only the real site may open a game socket. The browser smoke now runs in
Chromium, WebKit and Firefox.

**What is left is Rohan's:** deploy, then play. See "Left for next time".

## What did not work

- **§7.2 alone left the fix invisible.** The spec says to tint the blocking *tile*. It was implemented,
  and the first capture showed nothing: a prop now fills its hex exactly (§7.3, the other half of the
  same task), so from the game's camera the tile underneath it cannot be seen at all — and a wall or a
  pillar is the common blocker. The tile tint still answers for terrain (the plateau), and `PropView`
  now carries the same red when it is the blocker. Fixed in its own commit, with the before/after in
  the captures. The lesson is the one the spec itself gives: look at the picture, do not assume it.
- **The first attempt at the Editor proof ran against a Production server by accident.** `dotnet run
  --no-launch-profile` defaults `ASPNETCORE_ENVIRONMENT` to *Production*, which now loads the origin
  allow-list, so the Editor's socket — which sends no `Origin` — was refused with a 403 and the lobby
  just said "Server unreachable". Nothing was wrong with either half. **Use `dotnet run --project
  server/Mimas.Server`** (the launch profile sets `Development`), which is what `CLAUDE.md` documents.
- **`MIMAS_WEB_PATH=Build/Web` does not work from the repo root**: `dotnet run --project X` runs with
  the project directory as the working directory, so a relative path resolves under
  `server/Mimas.Server/` and the static-file branch stays inert (no "serving the web build from" line).
  An absolute path works. `CLAUDE.md`'s command is misleading; worth fixing next time something touches
  that file.
- **`SaveProjectSettings()` did not persist in batch mode.** §8.3 expected the build to leave the four
  identity values in `ProjectSettings.asset` and for that file to be committed; the build log proves
  the values were applied, and the file on disk did not change. It is not a new bug — the committed
  file also still records the old exception-support value that T-0003 believed it had written. What
  ships is what `WebBuild` sets at build time, which is the point of stating it in code. Recorded in
  `docs/hosting.md`; nothing under `ProjectSettings/` was committed.
- **Three blocked commands from the asset guard, all read-only false positives**, all from the guard
  scanning the whole command *text*: `ls .claude/protocols/` plus a `find … -not -path "*/Library/*"`;
  a `cat` of a Core test file whose command also contained `2>/dev/null`; a `grep -rln … --include=*.prefab
  --include=*.unity`; and a `grep` of `studio/game.yaml`. A fourth was genuine and useful: `git add` of
  a `.meta`, which is what sent me to `allows_assets`. Used the Read/Grep tools instead. That makes ten
  known false positives; the shape is unchanged.
- **Driving a *live* online match into a particular geometry is not worth it.** The 30 s server turn
  expires while a script is thinking, and the bot moves the board under you. The blocker capture was
  staged in a **local practice match** instead (no server, no clock), by walking the hero three real
  hexes and passing two turns — the rules path is untouched, and what is being photographed is the
  picture, which is exactly what the two new Core tests do *not* cover.
- `unity build` and `unity test` both refuse while an Editor has the project open (`already open in a
  running Editor`), so the order has to be: everything that needs a live Editor, then `unity close`,
  then the batch work. Worth knowing before planning a session.
- The `eval` harness reports **every** diagnostic including a trailing "Unreachable code detected";
  the real error is the *first* line, so never `tail -1` an `eval` failure. Also
  `Object.FindFirstObjectByType` is now obsolete-as-an-error there: use `FindAnyObjectByType`.
