# Run: Boons groundwork in Core — definitions, the unit overlay, elements, reveal, draft, session

> Opened at the start of the session and appended to as it goes. Not written at the end.

## What is different now

**Nothing a player can see, on purpose.** Part 1 of the boons is the rules engine growing the whole
system with tests: the game now knows what a lineage is, what a Blessing, an Enchant and a Sigil do, how a
unit is built from gear plus lineage plus boons, when the opponent learns about a boon, how three boons are
offered between rounds, and how a best-of-3 runs from one round to the next with everything learned
carried along. Three lineages ship — Greek (Athena's Guard), Norse (Thor's Vigour), Hindu (Vayu's Breath) —
with six boons each, using the spec's placeholder numbers. What a player sees (the lineage in the room, the
draft screen, boons in the examine panel, the "Revealed: Agni's Crown" flyover, the online best-of-3) is
part 2, T-0010, which needs its full spec written against this code first.

**Nine commits on `main`, Core only.** No server file changed and the 47 server tests never wavered; no
client file changed (the Editor regenerated the data manifest and the `.meta` files, nothing else). Core
tests 323 → 445.

**Commits 1–5 landed** (`c4d9c85`, `fb71fb3`, `d5d0e49`, `7b7d6d4`, `81fa69b`), 323 → 407 Core tests, 47
server tests untouched. The rules engine now knows what a boon is: `boons/` and `lineages/` load and
fail closed on every rule in spec §5; a unit is gear + lineage + boons through one overlay, every
contribution tagged with its boon; `MatchState.ResolveAbility` is the only ability lookup (a source
scan proves it); a Blessing's Strength is its own hidden damage line, an immunity is one `Nullify`
line, and an Enchant's element satisfies a rider; the six reveal rules of §6.5 fire and are tested
one by one; the view carries the lineage and the boons as id-or-null; the mirror rebuilds from
revealed boons; and a twelve-seed sweep with boons on both sides finds no leak. Nothing a player can
see yet: that is part 2.

**Two things decided inside the spec's silence**, both written into code comments and here:

1. **Boon and lineage reveals are keyed apart from ability and modifier reveals** (`boon:` / `lineage:`
   prefixes inside `MatchState`'s revealed set; `KnowsBoon` / `KnowsLineage` beside `Knows`). The spec
   ships boons whose id equals their modifier's (`apollo-eye`, `skadi-hide`, …) and says "no collision is
   possible" because events name their kind — but the revealed *set* is one namespace, so the first
   modifier reveal would have swallowed the boon's event. `RevealedEntries` carry the prefixed strings
   opaquely; the session hands them back unchanged.
2. **The preview counts one unknown per hidden boon** on each unit involved, not per hidden contribution.
   A hidden modifier already counts whether or not it applies, and a mirror (which holds no hidden boon at
   all) can only add back a count it can see: `HiddenBoonCount`. So a hidden boon that attaches a hidden
   modifier is two "?"s. Truth and mirror agree at every step of the sweep, which is the invariant.

**Commits 6–8** (`f16a194`, `2296ca1`, `73aa09c`): the draft as a pure seeded function; the `Session`
state machine with its filter, view and the bot's draft pick, proved by a golden replay (two seeds, bots on
both seats, 839 and 977 identical log lines to a 2-0 finish); and the shipped content of §5.8 with the
Editor's `.meta` files and the rebuilt manifest. **Commit 9** is the documentation: `data.md`, ADR-034 and
ADR-035, `architecture.md`, `networking.md`, the design page (every edit of spec §10.4, thirteen open
questions closed, the decision log and the changelog), STATE, this report.

**Two more small decisions inside the spec's silence:**

3. **The class is `Mimas.Core.Session.Session`**, as the spec's drift note names it. From another namespace
   the bare name resolves to the namespace, so callers alias it (`using Session = Mimas.Core.Session.Session;`
   inside their own namespace block) or write `Session.Session`. Part 2's server code will meet this.
4. **A player with zero offers is picked the moment the draft opens**, and a pick command from them is
   accepted as a no-op (spec §8 and §13 said both "counts as a pick of nothing" and "HasPicked is true
   immediately"; this satisfies both). Both players with zero offers means the next round starts in the
   `Apply` that ended the previous one, as §13 says.
