### 2. Finding 1 reproduced, and it is Unity's bug, not ours

Served `Build/Web` from `Mimas.Server` and drove it with the smoke harness (a new `type:` step was
added to it — `page.keyboard.type`, one character at a time with a 60 ms delay, like a player):

```
node tools/smoke/browser-smoke.mjs --shot artifacts/smoke-0918-type \
  --do "wait:4000,click:436,358,wait:500,shot:focused,type:abcd,wait:800,shot:typed,click:545,358,wait:2500,shot:joined"
```

- `artifacts/smoke-0918-type/typed.png` — the code field is still empty after typing `abcd`.
- `artifacts/smoke-0918-type/joined.png` — pressing **Join room** answers *"Type the code your friend
  sent you."*

So **pointer input works and keyboard text input does not.** The click reached the button; the
keystrokes never reached the `TextField`. Exactly Rohan's symptom.

The same applies to the **NAME** field, which nobody has noticed because it is pre-filled with
`Guest-NNNN`. In a browser today you cannot change your name either.

Root cause is upstream, and well known:

| Source | What it says |
|---|---|
| [discussions.unity.com, Apr 2026, U6.4 + Chrome](https://discussions.unity.com/t/ui-toolkit-textfield-webgl-u6-4-pc-chrome-is-dont-move/1717836) | UI Toolkit `TextField` in a Web build "briefly receives focus, but it immediately loses focus". Works in the Editor, works on mobile browsers. Unity staff asked for a bug report; it became issue **4006, "Input fields do not maintain focus when they are selected in a Web build"** |
| [Unity issue tracker](https://issuetracker.unity.com/issues/4006) | The issue exists. The tracker is a SPA and its fixed-in version could not be read from here |
| [discussions.unity.com](https://discussions.unity.com/t/keyboard-ontextinput-is-broken-in-webgl-new-input-system/873294) | `Keyboard.onTextInput` misbehaves on Web with the Input System package — Enter arrives as the literal characters `E n t e r` |
| [Unity issue tracker](https://issuetracker.unity3d.com/issues/unable-to-write-text-in-the-input-field-with-the-new-input-system-in-webgl-build) | The same class of failure for uGUI/TMP input fields with the Input System on Web — years old |

Relevant project facts: `activeInputHandler: 1` (Input System package **only**, legacy input off),
there is **no `EventSystem` in any scene** — UI Toolkit is running on its own `DefaultEventSystem` —
and the game's own input is `Mouse.current` / `Keyboard.current` (`BoardInputController`,
`CameraDirector`), not actions.

This is a decision for Rohan, not a fix an agent picks: see the options below.

### 3. Things the browser said that nobody had read yet

From the same run's console, all warnings, none fatal:

```
GL Driver Message (OpenGL, Performance, High): GPU stall due to ReadPixels   (x4, then suppressed)
Additional Lights Cookie Format (GrayscaleHigh) is not supported by the platform. Falling back to 32-bit
Shader 'Hidden/Universal Render Pipeline/Edge Adaptive Spatial Upsampling' is not supported
  (in 'Blit FSR Upscaling'). PostProcessing render passes will not execute.
```

The first is a synchronous GPU readback — golden rule 9's "no sync GPU readback" — and is a candidate
for finding 3. The third says the URP asset asks for FSR upscaling, whose shader does not exist on
WebGL2, and that **all post-processing is therefore silently skipped** in the browser.

Also visible in every screenshot: the canvas is **960×600 letterboxed inside a 1280×800 page**, with
the stock Unity footer bar. That is the default Web template. It is not what a friend should be sent
to on 10 Oct.

### 4. The jank: what could and could not be measured from here

Built `tools/smoke/browser-perf.mjs` — boots the served build, optionally clicks its way into a match,
then samples `requestAnimationFrame` deltas and reports p50/p95/p99, the worst ten frames and the count
over 33/50/100 ms. **Neither browser mode tells the truth about Rohan's machine:**

| Mode | What happened |
|---|---|
| headless | SwiftShader software rasteriser. Any frame number is fiction |
| headed | Ran the page at **236 fps** (p50 4.2 ms) — Playwright's Chromium composites without vsync — and **CDP mouse clicks never reached Unity**, even after `page.bringToFront()`. Both runs measured an idle lobby and reported a flawless 0 dropped frames |

So no frame-time verdict from automation. What the runs *did* settle:

- **The `GPU stall due to ReadPixels` warning is my own harness, not the game.** It appears 4 times
  headless and **zero times headed** (`artifacts/perf-0918-match/console.log`). Headless Chromium reads
  the canvas back to composite. Struck off the suspect list; golden rule 9 is not being broken.
- **`Shader 'Hidden/Universal Render Pipeline/Edge Adaptive Spatial Upsampling' is not supported
  (in 'Blit FSR Upscaling'). PostProcessing render passes will not execute.`** appears in **both**
  modes, so it is real on a real GPU. Post-processing is silently skipped in the browser today.
  The PC render-pipeline asset has `m_UpscalingFilter: 0` (Automatic) with `m_RenderScale: 1`.
- Three `Hidden/…` URP shaders report "not supported on this GPU" on WebGL2: `CoreSRP/CoreCopy`,
  `StencilDitherMaskSeed`, `Universal/HDRDebugView`.
- The client never touches `Application.targetFrameRate` (correct — Unity's Web manual says leave it at
  `-1` and let the browser drive rAF; setting it is a documented cause of stutter) and does no
  `ReadPixels`/`AsyncGPUReadback` anywhere.
- No per-frame allocation found by reading all seven `Update()` methods in the client.

### 5. The stock template is the whole of the presentation, and it is doing two things to us

`Build/Web/index.html` is Unity's **Default** template, unmodified. `Assets/WebGLTemplates/` does not
exist. Two lines matter:

```js
// desktop branch
canvas.style.width  = "960px";
canvas.style.height = "600px";
```

- The game is a **fixed 960×600 box** letterboxed in the page, with Unity's footer bar (logo,
  "MimasClient", fullscreen arrows) under it and the tab titled **"Unity Web Player | MimasClient"**.
  `companyName` is still `DefaultCompany`.
- `config.matchWebGLToCanvasSize` is left at its default `true`, which means Unity sizes the drawing
  buffer to the canvas's DOM size **multiplied by `window.devicePixelRatio`**. The template ships
  `config.devicePixelRatio = 1` commented out.
- The fullscreen button calls `unityInstance.SetFullscreen(1)`. On a 4K display that takes the drawing
  buffer from 960×600 to 3840×2160 — **14× the pixels** — with URP shadows at 2048 and HDR on.

**If Rohan pressed that fullscreen button, that alone is a complete explanation of the jank.** Not yet
confirmed with him.

### 6. Rohan's display, and why finding 3 is probably not a code bug

Asked him directly. **He pressed the fullscreen button, and the monitor is 2560×1440 at 144 Hz.**

| | Windowed (stock template) | Fullscreen on his monitor |
|---|---|---|
| Drawing buffer | 960×600 = 0.58 Mpx | 2560×1440 = 3.69 Mpx (**6.4×**), more if Windows display scaling puts `devicePixelRatio` above 1 |
| Frame budget | 6.94 ms (144 Hz) | 6.94 ms (144 Hz) |

So the browser is asked for 6.4× the pixels in the same 6.9 ms. The interesting part is not the average
frame rate: Unity Web renders inside `requestAnimationFrame`, so a frame that overruns 6.94 ms does not
degrade smoothly — it takes two vsync intervals. A run that alternates between one and two intervals
reads as dropped frames to a human, which is exactly the phrase he used. A *locked* 72 fps on a 144 Hz
panel would look smooth; an uneven 90–120 fps looks broken.

**Working conclusion: finding 3 is a presentation-layer defect, not a bug in the game code.** No
per-frame allocation, no `targetFrameRate` meddling and no readback exists in the client to explain it.
That makes finding 3 and the canvas question one decision rather than two.

It stays a hypothesis until a capped build is measured on his machine, because nothing here has been
measured at 144 Hz — the harness could not do it.

### 7. It is not "typing is broken" — it is *no text at all*

Three separate input routes were tried against the same served build, in one run
(`artifacts/smoke-0918-paste/`):

| Route | Playwright call | What it imitates | Result |
|---|---|---|---|
| Typed keys | `keyboard.type("abcd", {delay:60})` | a player typing | field stays empty |
| Inserted text | `keyboard.insertText("WXYZ")` | **a paste, and an IME commit** — text with no key events | field stays empty |
| Clipboard shortcut | `keyboard.press("Control+v")` | Ctrl+V | field stays empty |

After all three, **Join room** still answers *"Type the code your friend sent you."*

This matters more than it looks. The design page says a friend "joins by **pasting** either" the code or
the link (`#online`, rule 2, decided 17 Sep 2026, OPT-0001). **Pasting a code into the browser build does
not work today either.** Only the `?room=` link path works, because that never touches a text field.

It also rules out a whole family of fixes: anything that relies on Unity's own text pipeline reaching
the `TextField` — re-focusing it, an EventSystem, IME tricks — is aiming at a pipe that delivers
nothing. A working fix has to put the string in from outside: a DOM `<input>` the browser owns, or a
value set from C# (a keypad, a link, a `SetValueWithoutNotify`).

A new `insert:` step was added to `browser-smoke.mjs` for this, next to `type:`.

### 9. "Copy link" does not copy. There is currently no way for a second human to join at all

The researcher flagged `LobbyView.cs:355` (`GUIUtility.systemCopyBuffer = link`) as suspect on Web.
Checked it rather than assumed it — `tools/smoke/clipboard-check.mjs`: seed the real clipboard with a
sentinel, boot, press **Play vs bot**, press **Copy link**, read `navigator.clipboard.readText()`.

```
clipboard seeded: SENTINEL-BEFORE-COPY
click Copy link
  [LobbyView] copied http://localhost:7777/?room=VV8Y
clipboard after Copy link: "SENTINEL-BEFORE-COPY"
RESULT: it does NOT — "Link copied." is a lie in the browser.
```

The game logs the link, sets `systemCopyBuffer`, and tells the player **"Link copied."** The browser
clipboard is untouched. Unity's Web clipboard is its own enclosed buffer.

Put together with finding 7, **the browser build has no working way for a second human to join a room:**

| Path | State |
|---|---|
| Type the code | dead — no text reaches a `TextField` (Unity 4006) |
| Paste the code | dead — same |
| Press "Copy link", send it | dead — nothing is copied, and the player is told it was |
| `?room=CODE` in the address bar | **works** — but only if someone reads the code aloud and the friend types the URL by hand |

So M2-1 ("two browsers play a full match") is not one step away; it is behind two independent defects,
neither of them found by 34 server tests or by any ladder rung. This is what a human playing it buys.

The clipboard one is small and uncontroversial to fix — `navigator.clipboard.writeText()` from a jslib,
called inside the click gesture, with the Unity assignment kept for the Editor.

### 10. The resolution theory is wrong — measured, on the real GPU

Finding 6 argued the jank was fullscreen pixel load. It is not. Two bugs in my own probe had to be
fixed before it could say anything true:

1. **It clicked during the Unity splash.** "Booted" means `createUnityInstance` resolved; the splash is
   still on the canvas for seconds afterwards. Two runs clicked into the splash, never reached the
   arena, and measured the idle lobby — which I read as "headed Chromium swallows clicks". It does
   not. A `--warmup` (default 6 s) fixed it, and the run now logs
   `[MatchSession] online: match 4, seat 0 vs Random Bot` before sampling.
2. **Headed Chromium is on the real GPU.** Unity masks the renderer string to `WebKit WebGL` in both
   modes, but the extension lists give it away: headed advertises `EXT_disjoint_timer_query_webgl2`,
   `KHR_parallel_shader_compile` and `WEBGL_provoking_vertex`; headless advertises ASTC and ETC
   compressed textures, which only a software rasteriser claims. So headed numbers are real.

A `--size WxH` step resizes the canvas and lets Unity resize its drawing buffer to match — what the
fullscreen button does, without needing a fullscreen. In the arena, in a live bot match:

| Drawing buffer | Mpx | mean fps | p50 | p95 | p99 | max | frames >33 ms |
|---|---|---|---|---|---|---|---|
| 960×600 | 0.58 | 240 | 4.2 | 4.3 | 4.3 | 4.7 | 0 |
| **2560×1440** (his fullscreen) | **3.69** | **240** | **4.2** | **4.3** | **4.3** | **4.9** | **0** |
| 5120×2880 | 14.75 | 156 | 4.3 | 8.5 | 16.7 | 37.7 | 1 |

240 fps is Chromium's rAF ceiling here, so 4.2 ms means "finished inside 4.17 ms", not "took 4.2 ms".
The 5120×2880 row proves the instrument responds to load rather than reporting a constant.

**At the resolution Rohan actually played, the arena renders in under 4.17 ms on his GPU — against a
6.94 ms budget at 144 Hz. There is roughly 4× headroom.** Capping the resolution would have cost
sharpness and fixed nothing.

What this does *not* clear: the arena was **idle** in every run. Nothing moved, no unit animated, no
projectile flew, no shader met the GPU for the first time. The one interesting number in the whole set
is a single 58.3 ms frame in the first 960×600 run — one frame, early, exactly the shape of a shader
compiling on first use. Rohan's jank happened while *playing*.

So finding 3 is still open, and the remaining candidates are transient rather than steady: first-use
shader compilation, a GC hitch, an allocation on an event, or frame pacing in his real Chrome (this
harness runs at 240 Hz rAF and therefore does not reproduce his 144 Hz vsync at all).

**Next step for it: an in-game frame meter, not another harness run.** A probe that sits in the client,
counts frames over 50 ms and names what the game was doing, enabled by `?perf=1` on the page URL so it
needs no keyboard — which is broken anyway until the editor upgrade lands.
