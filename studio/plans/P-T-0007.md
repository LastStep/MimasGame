# Plan: Deploy — a link a friend can open

Written for Rohan, who does not read code. The detailed work order is `docs/specs/2026-09-22-deploy.md`;
this page is the shape of it.

## What this will do

The game gets a real address, `https://mimas.laststep.cloud`, on the VPS you already pay for, next to
your other site and without touching it. A friend clicks the link, the game loads, they join your room
by code. You deploy a new version with one command from this PC, and undo it with one command. The
first time, you follow a short document that sets the VPS up; after that it is the one command.

## Approach

1. **The server learns to listen only to the machine it is on.** One new setting. Today it listens on
   every address, which on a VPS with no firewall would mean the world could reach it without HTTPS.
2. **The deploy files are written.** The nginx block for the new address, a tiny bootstrap block so the
   certificate can be issued, the service definition that keeps the game server running and restarts it
   if it dies, a set-up script for the VPS, a release script for the VPS, and the one command for this PC.
3. **The one command does the whole thing.** Build the Web version, refuse if it is over 25 MB, build
   the Linux server, send both over your existing `ssh hostinger` connection, swap them in, restart, and
   check the live address answers. It also has a rehearsal mode that touches nothing remote.
4. **The smoke test learns to time itself**, so "how long does it take to load" becomes a number in
   the roadmap instead of a feeling.
5. **The runbook is written for you**: the DNS record, the set-up command, the deploy command, how to
   check, how to roll back, what each failure looks like.
6. **Everything is proved locally**: the rehearsal mode, the Linux server running inside WSL, the size
   gate refusing a fake limit, the smoke against a locally served build.
7. **You deploy.** Then a short session measures the live site, writes the baseline, and hands to a
   verifier.

## Choices made, and what lost

| Choice | Alternative | Why this one |
|---|---|---|
| Your existing VPS, `mimas.laststep.cloud` | New domain; Cloudflare Pages; a path under `laststep.cloud` | One machine, one nginx file, one cert; the name matches your existing subdomains; permanent |
| You run the deploy; agents only rehearse | Agent deploys over the alias | Your call on 22 Sep. The alias is in place, so automating later is a one-line change to the rule, not to the script |
| systemd + a self-contained Linux build | Docker (already on the box); installing .NET on the VPS | Nothing to install, nothing to keep in step, one file to read when it breaks |
| A separate certificate for the new name | Expanding the existing one | Expanding rewrites your other site's nginx file; we never touch it |
| `tar` over `ssh` | `rsync` | Git Bash on this PC has no rsync; `tar` is everywhere |
| Hard 25 MB gate in the script | No gate; a softer warning | The one-pager's number; the build is 12.3 MB today |

## How it gets proved

| Done-when | Proved by |
|---|---|
| Server bind flag | Rung 1, 2, 5 green; a curl to the LAN address fails while loopback answers |
| The six deploy files, secret-free | `bash -n` each; a grep for the IP, `root@`, `id_hostinger` returns nothing |
| Rehearsal mode works; the gate trips | `--dry-run` exit 0; `MIMAS_SIZE_LIMIT_MB=1` exit 1 |
| The Linux server runs | Started inside WSL; `/health` shows the same content hash as Windows |
| Smoke timing | Local smoke exit 0 with a `[timing]` line |
| Runbook and docs | Files exist with the sections the spec names; hosting.md no longer says Docker |
| Live (Part 3) | Smoke against the real URL exit 0 ×3; headers as listed; baseline written; playtest entry names a non-Rohan player |

## Risk

The VPS is shared with production things that are not ours. The set-up script keeps a backup of any
nginx file it replaces and restores it if `nginx -t` fails, and never opens the other site's file.
The certificate cannot be issued until the DNS record exists, so the runbook starts there and the script
checks it. The server binds to loopback, so a wrong nginx config exposes nothing. If the first deploy
fails at a step nobody foresaw, that is what Part 3 is for: the runbook's failure table grows.

Stop and report blocked if: `ssh hostinger` stops working from this PC, `dotnet publish` for Linux fails
in a way the spec's forks do not cover, or the Unity Web build fails and the 18 Sep build is gone.

## Size

Part 1: one Opus session, no warm Editor needed beyond one batch build. Part 2: an hour of Rohan's,
including waiting for DNS. Part 3: under an hour.
